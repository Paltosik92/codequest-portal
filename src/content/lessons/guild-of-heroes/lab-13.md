## Абстракция: abstract, protected и роль поддержки

> До совета Нижнего Брода — **11 дней**.

Утром Елена пришла в гильдию первой и долго смотрела на вчерашнюю ведомость.

— «Сергей — один, один, один», — прочитала она вслух, когда собрались остальные. — Знаете, что здесь неправильно?

— Что Сергей — один? — предположил Артём.

— Что Сергей — **«просто герой»**. В программе есть воины, маги, лучники — и ещё какие-то «просто герои», которые вкладывают свою выучку во что угодно. Даже в печать.

— А что, нельзя? — Александр почесал бороду. — Сергей же не умеет читать печати.

— Вот именно. — Елена повернулась к Сергею. — Ты не «просто». Ты делаешь так, чтобы остальные **могли** работать. Крепления, страховка, клинья. Это профессия.

Сергей покраснел и уставился в стол.

— Я просто креплю, — пробормотал он. — Чтобы ничего не упало.

— А это и есть роль, — сказала Анастасия. — Поддержка.

## Цель и результат

После этой работы вы:

- сделаете класс `Hero` **абстрактным** — «героев без роли» больше не бывает;
- объявите **абстрактный** метод `GetContribution` — каждый наследник обязан ответить сам;
- закроете конструкторы `Hero` модификатором **`protected`** — их вызывают только наследники;
- вынесете общий для профессий расчёт в `protected`-помощник;
- создадите роль поддержки `SupportHero` и переведёте в неё Сергея;
- добавите героям название роли, которое видно в окне.

**Результат:** в мире не осталось ни одного «просто героя». Сергей — поддержка с выучкой 5, он в отряде №202, и в ведомости у него 5 / 5 / 5.

## Обязательная часть

### 1. «Просто герой» читает печать

Проверим, что умеет герой без роли. Замените тело `Probe.Run`:

```csharp
public static void Run() {
    Console.WriteLine(">>> Проба <<<");

    Hero nobody = new Hero("Учебный никто", 100, 7);
    Challenge seal = new Challenge(ChallengeKind.Seal, 10);
    Challenge rubble = new Challenge(ChallengeKind.Rubble, 20);

    Console.WriteLine($"Печать: {nobody.GetContribution(seal)}");
    Console.WriteLine($"Завал: {nobody.GetContribution(rubble)}");
}
```

Включите пробу и запустите:

```text
>>> Проба <<<
Печать: 7
Завал: 7
```

Герой без профессии вложил 7 в печать — больше, чем маг с выучкой 3. Почему? Потому что в №12 мы дали `Hero` ответ «по умолчанию» — и этот ответ подходит **никому**. Воин, маг и лучник его заменили. А «просто герой» остался с ответом, который ничего не значит.

Значит, у `Hero` вообще **нет** правильного ответа на вопрос «чем ты поможешь?». Ответ есть только у конкретной роли. И создавать героя «без роли» не должно быть можно.

Выключите пробу и очистите `Run`.

### 2. Абстрактный класс

Откройте `Hero.cs` и добавьте в заголовок одно слово:

```csharp
public abstract class Hero {
```

**`abstract class`** — абстрактный класс. Он описывает **общее** для своих наследников, но объект прямо из него создать нельзя. `new Hero(...)` — ошибка компиляции: «невозможно создать экземпляр абстрактного типа». Создаются только наследники: воин, маг, лучник.

Переменные типа `Hero` при этом остаются: `List<Hero>`, `Hero? AssignedHero`, `foreach (Hero member in ...)`. В них лежат воины и маги — как и раньше. Запрещено создавать **объект самого `Hero`**; хранить ссылки на его наследников по-прежнему можно.

Теперь сам метод. Замените `virtual`-версию на:

```csharp
public abstract int GetContribution(Challenge challenge);
```

**Абстрактный метод** — метод без тела: только заголовок и точка с запятой. Он говорит: «у каждого героя **есть** ответ на этот вопрос, но какой — решает наследник». Абстрактные методы бывают только в абстрактных классах.

| | `virtual` (№12) | `abstract` |
| --- | --- | --- |
| Тело в базовом классе | есть — ответ по умолчанию | нет |
| Наследник | **может** переопределить | **обязан** переопределить |
| Забыл `override` | тихо работает версия родителя | ошибка компиляции |

Последняя строка важна. В №12 потерянный `override` молча ломал расчёт. Теперь компилятор не даст собрать проект, пока каждый наследник не ответит сам.

![Абстрактный стул: нарисован, подписан — а сесть нельзя](/materials/guild-of-heroes/img/lab13/meme-01-abstract-chair.webp)

Сохраните и соберите проект. Ошибка будет в одном месте — в `WorldSetup`:

```csharp
Hero sergey = new Hero("Сергей", 110);
```

«Просто героя» создать больше нельзя. Сергею нужна роль.

### 3. Роль поддержки

Создайте `SupportHero.cs`:

```csharp
public class SupportHero : Hero {
    public SupportHero(string name, int health, int training) : base(name, health, training) {
    }

    public override int GetContribution(Challenge challenge) {
        return Training;
    }
}
```

Поддержка не двигает балки и не читает печати. Она делает так, чтобы **любое** испытание вообще можно было начать: страховка, крепления, свет. Поэтому её вклад одинаков везде — вся выучка.

Похоже на бывший ответ «по умолчанию»? Да. Но разница принципиальная: раньше это был ответ **«не знаю, кто ты»**, а теперь — осознанное решение роли поддержки.

В `WorldSetup.Create` замените строку Сергея:

```csharp
Hero sergey = new SupportHero("Сергей", 110, 5);
```

Сергей — поддержка с выучкой 5. Проект снова собирается.

### 4. Конструкторы для наследников: protected

Конструкторы `Hero` всё ещё `public`. Но вызвать их снаружи теперь невозможно — `new Hero(...)` запрещён. Их зовут только наследники через `base(...)`. Скажем это явно. Замените `public` на `protected` у **обоих** конструкторов `Hero`:

```csharp
protected Hero(string name, int health, int training) {
    // ... тело без изменений ...
}

protected Hero(string name, int health) : this(name, health, 1) {
}
```

**`protected`** — доступ для **своего класса и наследников**. Снаружи (из `Program`, окна, доски) такой член не виден, а внутри `Warrior`, `Mage`, `SupportHero` — виден.

| Модификатор | Внутри `Hero` | Внутри наследника | Снаружи |
| --- | --- | --- | --- |
| `public` | да | да | да |
| `protected` | да | да | **нет** |
| `private` | да | **нет** | **нет** |

Зачем конструктор классу, объект которого нельзя создать? Затем, что **каждый** воин, маг и поддержка при рождении проходит через этот конструктор: имя обрезается, здоровье и выучка проверяются. Абстрактный класс не создаёт объектов сам, но участвует в создании каждого наследника.

![При создании одного SupportHero сначала выполняется конструктор Hero через base, затем тело конструктора SupportHero](/materials/guild-of-heroes/img/lab13/schema-04-abstract-construction.webp)

Проверьте себя — верно или нет?

1. `List<Hero> team = new List<Hero>();` — ошибка: `Hero` абстрактный.
2. `Hero h = new SupportHero("С", 100, 5);` — допустимо.
3. Из `GuildConsole` можно вызвать `new Mage("М", 90, 6)`, хотя конструктор `Hero` — `protected`.
4. Наследник может не переопределять `GetContribution`, если ему подходит ответ `Hero`.
5. Абстрактный класс может содержать обычные методы с телом.

<details>
<summary>Ответы</summary>

1 — неверно: список **ссылок** типа `Hero` создать можно, нельзя создать **объект** `Hero`. 2 — верно: объект — поддержка, переменная — герой. 3 — верно: снаружи вызывается **публичный** конструктор `Mage`, а уже он через `base(...)` зовёт защищённый конструктор `Hero`. 4 — неверно: у `Hero` больше нет ответа, абстрактный метод обязаны переопределить все. 5 — верно: `TakeDamage`, `GainExperience`, `GetInfo` — обычные методы абстрактного класса.

</details>

### 5. Общий расчёт — в protected-помощник

Посмотрите на три `override`: у воина, мага и лучника повторяется `return Training / 2;` — «помощь не по специальности». Одно и то же правило записано трижды. Изменит Елена правило — придётся найти все три места.

Вынесем его в `Hero`, но так, чтобы снаружи его не было видно: это внутренняя деталь расчёта, а не вопрос, который задают героям. Добавьте в `Hero`:

```csharp
protected int GetSideHelp() {
    return Training / 2;
}
```

И замените в трёх наследниках `return Training / 2;` на:

```csharp
return GetSideHelp();
```

`Warrior.GetContribution` теперь выглядит так:

```csharp
public override int GetContribution(Challenge challenge) {
    if (challenge.Kind == ChallengeKind.Rubble) {
        return PushObstacle();
    }
    if (challenge.Kind == ChallengeKind.Seal) {
        return 0;
    }
    return GetSideHelp();
}
```

Проверим границы доступа. Замените тело `Probe.Run`:

```csharp
public static void Run() {
    Console.WriteLine(">>> Проба <<<");

    Warrior warrior = new Warrior("Учебный воин", 150, 6);
    Challenge height = new Challenge(ChallengeKind.Height, 5);

    Console.WriteLine($"Через GetContribution: {warrior.GetContribution(height)}");
}
```

Запустите — `Через GetContribution: 3`. Теперь допишите строку и посмотрите на ошибку:

```csharp
Console.WriteLine(warrior.GetSideHelp());
```

Компилятор: «недоступен из-за уровня защиты». `Probe` — не наследник `Hero`. Снаружи героев спрашивают только `GetContribution`, а как они считают ответ внутри — их дело. Удалите строку, выключите пробу и очистите `Run`.

![Что видно снаружи, а что — только внутри семейства Hero](/materials/guild-of-heroes/img/lab13/schema-01-access-levels.webp)

### 7. Абстракция — это договор

Посмотрите на `Hero` целиком. Это всё ещё большой класс с полями, свойствами, проверками и методами: `TakeDamage`, `Heal`, `GainExperience`, `GetInfo`. Абстрактный класс — не «пустой» класс. Он:

- **хранит** то, что одинаково у всех героев (здоровье, опыт, выучка);
- **делает** то, что все герои делают одинаково (получают урон, растут в уровне);
- **требует** то, что каждая роль делает по-своему (`abstract GetContribution`);
- **помогает** наследникам общими деталями (`protected GetSideHelp`);
- **запрещает** существовать без роли (`new Hero` невозможен).

Каждый наследник подписывает этот договор: «я — герой; всё общее беру у `Hero`; на вопрос о вкладе отвечаю сам». Компилятор проверяет, что договор выполнен.

Как решить в своём коде — `abstract` или `virtual`?

| Вопрос | Ответ «да» → |
| --- | --- |
| Может ли существовать объект базового класса сам по себе? | обычный класс; «нет» → `abstract class` |
| Есть ли у метода разумный ответ, общий для большинства наследников? | `virtual` с этим ответом |
| Ответ по умолчанию подходит «никому» или опасен (как вклад «просто героя» в печать)? | `abstract` |
| Деталь нужна наследникам, но снаружи о ней знать не должны? | `protected` |

### 8. Члены Hero по видам

Соберём в одну таблицу, какие члены теперь есть у `Hero` и почему каждый объявлен именно так.

| Член `Hero` | Вид | Зачем |
| --- | --- | --- |
| `Health`, `Experience`, `Training`… | обычные свойства | общее состояние |
| `TakeDamage`, `GainExperience`… | обычные методы | общее поведение |
| `GetContribution` | `abstract` | у каждой роли свой ответ, ответа по умолчанию нет |
| `GetSideHelp` | `protected` | общая деталь расчёта — только для наследников |
| конструкторы | `protected` | создают героя только через роль |

![Hero — договор: что даёт, что требует, что прячет](/materials/guild-of-heroes/img/lab13/schema-03-abstract-contract.webp)

| `Warrior.cs`, `Mage.cs`, `Ranger.cs` | `Training / 2` заменено на `GetSideHelp()` |
| `SupportHero.cs` | новый файл: роль поддержки |

### 10. Найдите две ошибки

#### Ошибка 1. Мастер на пятнадцать

Кто-то решил, что Сергей заслуживает больше, и дописал в конструктор `SupportHero`:

```csharp
Training = 15;
```

Компилятор не дал: у `Training` — `private set`. Тогда в `Hero` заменили объявление:

```csharp
public int Training { get; protected set; }
```

Собралось. Ведомость: «Сергей: 15 / 15 / 15», печать — 27. Как выучка 15 прошла мимо проверки `MaxTraining`? Почему `protected set` здесь хуже, чем `private set`?

#### Ошибка 2. Помощник наружу

Другой студент решил, что `GetSideHelp` пригодится в окне, сделал его `public` и написал ведомость так:

```csharp
Console.WriteLine($"{hero.Name}: {hero.GetSideHelp()} / {hero.GetSideHelp()} / {hero.GetSideHelp()}");
```

Ведомость: «Ярослав: 2 / 2 / 2», «Анастасия: 3 / 3 / 3», «Сергей: 2 / 2 / 2»… А суммы заслона над ней — правильные. Что не так в ведомости и почему `protected` защищал от этой ошибки?

<details>
<summary>Самопроверка — после своей попытки</summary>

1. Проверка `MaxTraining` есть только в конструкторе `Hero`. Тело `SupportHero` выполнилось **после** него и записало 15 в обход проверки. `protected set` открыл запись всем наследникам — и правило «выучка 1…10» перестало быть защищено. Исправление: вернуть `private set`, убрать `Training = 15`, а выучку передавать в `base(...)` — там её проверят.
2. `GetSideHelp` — «помощь не по специальности», часть внутреннего расчёта. Это не вклад героя. Снаружи правильный вопрос один — `GetContribution(challenge)`. Пока помощник был `protected`, вызвать его из окна было нельзя, и такой ошибки не могло случиться. Исправление: вернуть `protected`, в ведомости вызывать `GetContribution`.

</details>

### 11. Самостоятельный шаг

#### 11.1. Название роли

Добавьте в `Hero` абстрактное свойство:

```csharp
public abstract string RoleName { get; }
```

Абстрактными бывают не только методы, но и свойства. Реализуйте его в каждой роли через `override` — свойство только для чтения, которое возвращает «Воин», «Маг», «Лучник», «Поддержка».

В `GuildConsole.ShowMembers` выводите роль в скобках после имени:

```text

Сергей (Поддержка): здоровье 110, уровень 2, опыт 50, до уровня 50, выучка 5
```

#### 11.2. Второй помощник

`PushObstacle`, `ReadSeal` и `ReachHeight` считают одно и то же — «выучка × 2». Это тоже общее правило, записанное трижды.

1. Добавьте в `Hero` `protected`-метод `GetSpecialtyHelp()` — помощь по специальности.
2. Перепишите три умения через него.
3. Это рефакторинг: проверьте его через `diff` (как в №10) на вводе `printf '1\n7\n'`.

Объясните в README, почему `GetSpecialtyHelp` — `protected`, а `PushObstacle` остаётся `public`.

### 12. Перенос в личный проект

1. Сделайте базовый класс вашей темы **абстрактным**: можно ли в вашем мире «просто книгу» без вида? «Просто товар»? Если нельзя — `abstract`.
2. Метод-ответ из №12 сделайте `abstract`, если у базового класса нет осмысленного ответа по умолчанию. Если есть — оставьте `virtual` и объясните в README почему.
3. Конструкторы базового класса — `protected`.
4. Найдите повторяющийся расчёт в наследниках и вынесите его в `protected`-помощник.
5. Добавьте третьего наследника и убедитесь, что контейнер и окно его принимают без изменений.

Образец для библиотеки (у вас — свои классы):

```csharp
public abstract class Book {
    public string Title { get; private set; }

    protected Book(string title) {
        Title = title.Trim();
    }

    public abstract int GetLoanDays();

    protected int GetBaseDays() {
        return 14;
    }
}

public class Novel : Book {
    public Novel(string title) : base(title) {
    }

    public override int GetLoanDays() {
        return GetBaseDays();
    }
}
```

В README ответьте:

- почему ваш базовый класс абстрактный (или почему нет);
- что видят наследники, но не видит `Program`.

### Приложение Б. Если что-то не так

| Признак | Что проверить |
| --- | --- |
| «Невозможно создать экземпляр абстрактного типа» | Где-то осталось `new Hero(...)` — в `WorldSetup`, `Probe` или личном проекте |
| «Не реализует унаследованный абстрактный член» | В наследнике нет `override GetContribution` или `override RoleName` |
| «Абстрактный метод не может иметь тела» | У `GetContribution` в `Hero` осталось тело `{ return Training; }` |
| `GetSideHelp` «недоступен из-за уровня защиты» | Вызов снаружи — так и задумано; снаружи спрашивайте `GetContribution` |
| `base(...)` «недоступен» в наследнике | Конструктор `Hero` стал `private`, а нужен `protected` |
| Выучка больше 10 | Где-то `protected set` у `Training` и присваивание в наследнике |
| Сергей «1 / 1 / 1» | Сергей не переведён в `SupportHero` с выучкой 5 |
| Суммы заслона без +5 | Сергей не добавлен в экспедицию №202 |
| `diff` после 11.2 не пустой | `GetSpecialtyHelp` считает не `Training * 2` |
