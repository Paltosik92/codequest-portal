## Исключения: throw, try/catch и собственное исключение

> До совета Нижнего Брода — **8 дней**.

Утром курьер канцелярии оставил у окна приёма пачку накладных. Сергей разбирал их и вносил в журнал поставок экспедиции — привычно, строчка за строчкой.

На одной он остановился.

— «Уплотнения медные. Количество: минус шесть. Подпись: Сергей», — прочитал он вслух.

Елена заглянула в экран. Программа уже приняла накладную. В журнале стояло: «Уплотнения медные × 1, подпись: Сергей».

— Минус шесть превратилось в единицу, — сказала она. — Конструктор поправил. Как мы его учили с самого начала: «меньше одного — значит, один».

— Я этого не подписывал, — тихо сказал Сергей. — И минус шесть — это не количество.

— Это след, — Анастасия взяла бумагу. — Кто-то списывает уплотнения. И подписывается твоим именем.

— А наша программа этот след стёрла, — Елена откинулась на спинку стула. — Теперь в журнале обычная поставка на одну штуку. Правдоподобная ложь.

## Обязательная часть

### 1. Тихое исправление — это ложь

Воспроизведём то, что случилось утром. Замените тело `Probe.Run`:

```csharp
public static void Run() {
    Console.WriteLine(">>> Проба <<<");

    Expedition trial = new Expedition(1, "Учебная");
    trial.AddSupply("Уплотнения медные", 12, "Учебный мастер");
    trial.AddSupply("Уплотнения медные", -6, "Учебный мастер");

    foreach (SupplyEntry supply in trial.GetSupplies()) {
        Console.WriteLine(supply.GetInfo());
    }
    Console.WriteLine($"Всего: {trial.TotalQuantity("Уплотнения медные")}");
}
```

Включите пробу и запустите:

```text
>>> Проба <<<
Уплотнения медные × 12, подпись: Учебный мастер
Уплотнения медные × 1, подпись: Учебный мастер
Всего: 13
```

С №3 мы «нормализуем» данные: отрицательное здоровье становится 0, пустое имя — «Безымянный герой», награда меньше 1 — единицей. Для здоровья героя это разумно: урон не может увести его в минус. Но накладная — **документ**. Если в документе написано −6, это не опечатка, которую можно тихо поправить, — это **неверный документ**. Исправив его, программа:

- спрятала подделку: −6 исчезло, вместо него появилась правдоподобная единица;
- исказила итог: 13 вместо 12;
- никому ничего не сказала.

![Писарь-фокусник превращает «−6» в «1» взмахом пера](/materials/guild-of-heroes/img/lab16/meme-01-minus-six-to-one.webp)

Выключите пробу и очистите `Run`.

### 2. Два вида «нет»

Почему не вернуть `false`, как наши `TryAssign` и `TryComplete`? Потому что это **разные** «нет».

| | Предметный отказ | Неверные данные |
| --- | --- | --- |
| Пример | герой занят; вклада не хватает; поручение уже выполнено | количество −6; пустая позиция; накладная без подписи |
| Что это значит | всё правильно, просто **сейчас** нельзя | так **не бывает**: объект с такими данными не должен существовать |
| Нормально ли это | да, обычная ситуация | нет, где-то ошибка или обман |
| Как сообщаем | `false` из метода `Try…` | **исключение** |

К тому же конструктор вообще не умеет возвращать `false`: он либо создаёт объект, либо… Вот это «либо» и есть исключение.

### 3. throw: конструктор отказывается создавать объект

Откройте `SupplyEntry.cs` и замените тело конструктора:

```csharp
public SupplyEntry(string item, int quantity, string signer) {
    if (string.IsNullOrWhiteSpace(item)) {
        throw new ArgumentException("В накладной не указана позиция.");
    }
    if (quantity < 1) {
        throw new ArgumentException($"Количество должно быть положительным, а не {quantity}.");
    }
    if (string.IsNullOrWhiteSpace(signer)) {
        throw new ArgumentException("Накладная без подписи.");
    }

    Item = item.Trim();
    Quantity = quantity;
    Signer = signer.Trim();
}
```

**`throw`** — бросить исключение. `new ArgumentException("...")` создаёт объект-исключение — «неверный аргумент» — с сообщением. После `throw` метод **немедленно прекращается**: следующие строки не выполняются, объект **не создаётся**.

`ArgumentException` — готовый класс исключения из .NET. Своё сделаем чуть позже.

Включите пробу из шага 1 и запустите. Программа **упадёт**:

```text
>>> Проба <<<
Unhandled exception. System.ArgumentException: Количество должно быть положительным, а не -6.
   at SupplyEntry..ctor(String item, Int32 quantity, String signer) in ...\SupplyEntry.cs:line 7
   at Expedition.AddSupply(String item, Int32 quantity, String signer) in ...\Expedition.cs:line ...
   at Probe.Run() in ...\Probe.cs:line ...
```

Первая накладная даже не напечаталась: программа остановилась раньше, на второй. Прочитайте сообщение снизу вверх — это **путь исключения**: `Probe.Run` вызвал `AddSupply`, тот — конструктор `SupplyEntry`, а конструктор бросил исключение. Оно пролетело через `AddSupply` и `Probe.Run` наверх — и, никем не пойманное, остановило программу.

Ложь больше не проходит. Но и программа падает. Нужно исключение **поймать**.

### 4. try/catch: поймать и сообщить

Замените тело `Probe.Run`:

```csharp
public static void Run() {
    Console.WriteLine(">>> Проба <<<");

    Expedition trial = new Expedition(1, "Учебная");
    trial.AddSupply("Уплотнения медные", 12, "Учебный мастер");

    try {
        trial.AddSupply("Уплотнения медные", -6, "Учебный мастер");
        Console.WriteLine("Вторая накладная принята.");
    } catch (ArgumentException ex) {
        Console.WriteLine($"Отклонено: {ex.Message}");
    }

    Console.WriteLine($"Поставок: {trial.GetSupplies().Count}");
    Console.WriteLine($"Всего: {trial.TotalQuantity("Уплотнения медные")}");
}
```

Запустите:

```text
>>> Проба <<<
Отклонено: Количество должно быть положительным, а не -6.
Поставок: 1
Всего: 12
```

Как это работает:

- **`try { ... }`** — «попробуй выполнить». Если внутри брошено исключение, оставшиеся строки блока **пропускаются** — «Вторая накладная принята» не напечаталась.
- **`catch (ArgumentException ex) { ... }`** — «если прилетело исключение этого типа — выполни это». В переменной `ex` — сам объект-исключение, `ex.Message` — его сообщение.
- После `catch` программа **продолжает работу** как обычно.

Итог честный: одна поставка, 12 уплотнений, а про вторую — понятное сообщение.

`catch` ловит **только** исключения указанного типа и его наследников. Например, `ArgumentOutOfRangeException` при обращении к несуществующему элементу списка наследует `ArgumentException` — поэтому этот `catch` поймает и его. Он может ошибочно представить ошибку индекса как неверную накладную. Исключение из другой ветки, например `InvalidOperationException`, этот `catch` не поймает: оно пойдёт дальше вверх. Чтобы обрабатывать именно ошибки записей, на следующем шаге создадим отдельный тип.

Выключите пробу и очистите `Run`.

### 5. Своё исключение

`ArgumentException` бросают многие методы .NET — при самых разных ошибках. Если окно будет ловить `ArgumentException`, оно поймает и наши проверки накладных, и чужие ошибки, о которых мы ничего не знаем, — и покажет их человеку как «накладная отклонена». Нам нужен **свой** тип: «запись не прошла проверку» — и ничего больше.

Создайте `InvalidRecordException.cs`:

```csharp
public class InvalidRecordException : Exception {
    public InvalidRecordException(string message) : base(message) {
    }
}
```

Это обычное наследование из №11: `Exception` — базовый класс всех исключений .NET. Наш класс добавляет только **имя** — и этого достаточно, чтобы ловить именно его. Сообщение передаём в конструктор родителя через `base(message)`, и оно будет доступно как `ex.Message`.

По договорённости имена классов исключений оканчиваются на `Exception`.

В конструкторе `SupplyEntry` замените все три `ArgumentException` на `InvalidRecordException`:

```csharp
throw new InvalidRecordException($"Количество должно быть положительным, а не {quantity}.");
```

Теперь любой, кто увидит `catch (InvalidRecordException ex)`, сразу поймёт: здесь обрабатываются неверные записи.

![Типы исключений: ArgumentOutOfRangeException входит в ветку ArgumentException, InvalidRecordException — отдельная ветка](/materials/guild-of-heroes/img/lab16/schema-04-catch-types.webp)

### 6. Экспедиция: проверка переехала в запись

В №15 `Expedition.AddSupply` сама проверяла позицию и подпись на пустоту. Теперь это делает конструктор записи — и делает строже: с сообщением. Две проверки в одном месте не нужны. Упростите метод:

```csharp
public bool AddSupply(string item, int quantity, string signer) {
    return _supplies.Add(new SupplyEntry(item, quantity, signer));
}
```

Сначала вычисляется аргумент `Add`: вызывается конструктор `SupplyEntry`. Если он бросил исключение, до добавления в журнал дело не дойдёт. Две ветки схемы — независимые попытки из одного состояния, а не последовательность действий.

![Сначала создаётся SupplyEntry: неверная накладная не меняет журнал, правильная добавляет одну запись](/materials/guild-of-heroes/img/lab16/schema-05-create-before-add.webp)

Обратите внимание: здесь **нет** `try`/`catch`. Экспедиция не знает, что делать с неверной накладной: показать сообщение? записать в журнал? Это решает тот, кто её вызвал. Поэтому исключение просто **пролетает** через `AddSupply` дальше, к вызывающему.

Правило: ловите исключение там, где **знаете, что с ним делать**. Модель бросает, окно ловит и показывает.

### 7. Пункт «Накладная»

Накладные приходят каждый день, и вносить их через пробу — не дело. Добавим в окно приём накладных. Добавьте в `GuildConsole`:

```csharp
private void AcceptSupply() {
    Expedition? expedition = _board.FindExpedition(201);
    if (expedition == null) {
        Console.WriteLine("Экспедиция №201 не найдена.");
        return;
    }

    string? item = ReadInput("Позиция: ");
    if (item == null) {
        _isRunning = false;
        return;
    }

    string? quantityText = ReadInput("Количество: ");
    if (quantityText == null) {
        _isRunning = false;
        return;
    }
    if (!int.TryParse(quantityText, out int quantity)) {
        Console.WriteLine("Количество — это целое число.");
        return;
    }

    string? signer = ReadInput("Подпись: ");
    if (signer == null) {
        _isRunning = false;
        return;
    }

    try {
        expedition.AddSupply(item, quantity, signer);
        Console.WriteLine("Накладная принята.");
    } catch (InvalidRecordException ex) {
        Console.WriteLine($"Накладная отклонена: {ex.Message}");
    }
}
```

В `HandleChoice` — ветка `case "8": AcceptSupply(); break;`, в строке меню — `8 Накладная` перед `0 Выход`. Пунктов стало восемь — это предел нашего правила: дальше меню будет меняться, а не расти.

Посмотрите, как поделены проверки — это граница из №9:

- **окно** проверяет **форму**: пришло ли что-то; похоже ли «количество» на целое число. Здесь `int.TryParse`, а не `TryParseQuestId`: `−6` — правильная запись числа, и окно её пропускает;
- **модель** проверяет **смысл**: может ли быть такое количество. Это решает конструктор `SupplyEntry`;
- окно **ловит** исключение модели и переводит его на человеческий язык.

Запустите и попробуйте три накладные:


```text

Количество: два

```


Почему во втором примере нет слов «Накладная отклонена»? Потому что до модели дело не дошло: окно само увидело, что «два» — не число, и даже не спросило подпись. Ошибку формы ловит окно, ошибку смысла — модель.

### 8. Правило проекта: исключение или false

Запишем правило один раз — оно будет действовать до конца курса.

| Ситуация | Что это | Как сообщаем |
| --- | --- | --- |
| Накладная на −6 | неверные данные | `InvalidRecordException` |
| Накладная без подписи | неверные данные | `InvalidRecordException` |
| Герой занят другим поручением | предметный отказ | `TryAssign` → `false` |
| Вклада экспедиции не хватает | предметный отказ | `TryCompleteWithChallenge` → `false` |
| Поручение уже выполнено | предметный отказ | `TryComplete` → `false` |
| Номер в окне — не число | ошибка ввода человека | окно само отвечает подсказкой |

Методы с приставкой `Try` обещают: «я не брошу исключение, я отвечу `true` или `false`». Конструкторы и обычные методы обещают: «если данные неверные — брошу».

А как быть с остальными «тихими исправлениями» в проекте? Не всё нужно превращать в исключения. Вопрос один: это **документ**, который нельзя подправить, или **состояние**, у которого есть законные границы?

| Где | Что исправляется | Решение |
| --- | --- | --- |
| `Hero.TakeDamage` | здоровье ниже 0 → 0 | оставить: у состояния есть граница |
| `Hero`, конструктор | выучка выше 10 → 10 | оставить: правило устава «не больше 10» |
| `PumpMachine` | мощность 1…10 | оставить: паспортный предел механизма |
| `SupplyEntry` | количество < 1 | **исключение**: документ |
| `ObservationEntry` | пустой текст | **исключение** (шаг 11.1) |
| `Quest` | награда < 1, пустое название | **исключение** (шаг 11.2) |

![Два вида «нет»: false для отказа, исключение для неверных данных](/materials/guild-of-heroes/img/lab16/schema-03-two-kinds-of-no.webp)

### 11. Самостоятельный шаг

#### 11.1. Пустое наблюдение

В №15 правило «пустое наблюдение не записываем» жило в `Expedition.AddObservation` и отвечало `false`. Но пустое наблюдение — это неверные данные, а не отказ.

1. В конструкторе `ObservationEntry`: пустой или пробельный текст — `InvalidRecordException` с понятным сообщением. Пустое место по-прежнему заменяется на «Место не указано» — это не ошибка, а отсутствие уточнения.
2. Из `Expedition.AddObservation` уберите проверку — пусть работает конструктор.
3. Проверьте пробой с `try`/`catch`: пустое наблюдение отклонено с вашим сообщением, нормальное — принято.
