## Шаг 1. Зачем база, если есть файл

Файл `catalog.json` — это просто текст. Он ничего не знает о своих данных: в него можно записать скидку −500%, жанр «Гонкии» и две игры с одинаковым `id`, и он промолчит. Если два человека одновременно откроют и сохранят его, победит тот, кто сохранил последним.

**СУБД** (система управления базами данных) — программа, которая хранит данные и **отвечает за них**:

- проверяет правила: «скидка от 0 до 90», «у игры обязательно есть жанр»;
- даёт многим программам работать с данными одновременно и не терять правки;
- быстро отвечает на вопросы о данных на специальном языке — **SQL**.

PostgreSQL устроена так же, как наш сервер из №14: это программа, которая постоянно работает и ждёт подключений. Только разговаривает она не по HTTP, а по своему протоколу, и не на порту 5080, а на **5432**.

```text
psql (клиент) ──► сервер PostgreSQL 127.0.0.1:5432
                    ├─ база pixelport_sql_is31_ivanov    ← сегодня: учебная, для SQL
                    ├─ база pixelport_app_is31_ivanov    ← №18: база приложения
                    └─ базы других студентов (к ним тебя не пустят)
```

Данные хранятся в **таблицах**: строка — одна запись (одна игра), столбец — одно свойство (цена). У каждого столбца строгий тип, как у поля в C#.

## Шаг 2. Подключаемся

Открой терминал Git Bash в корне проекта и задай параметры **своими** значениями от преподавателя:

```bash
export PGHOST=127.0.0.1
export PGPORT=5432
export PGUSER=is31_ivanov
export PGDATABASE=pixelport_sql_is31_ivanov
export PGCLIENTENCODING=UTF8
```

`PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` — стандартные переменные, которые psql читает сам, чтобы не писать параметры в каждой команде. `PGCLIENTENCODING=UTF8` — чтобы русские буквы не превратились в «кракозябры». Пароля здесь нет: его psql спросит сам. Переменные живут, пока открыт терминал. Закрыл — задай снова.

Подключись:

```bash
psql -X
```

Введи пароль (символы не отображаются — так и должно быть). Приглашение сменится на `pixelport_sql_is31_ivanov=>` — теперь ты разговариваешь с базой, а не с Git Bash. `-X` — не читать личные настройки psql: на общем компьютере там может оказаться что угодно.

> Если после ввода команды ничего не происходит и приглашение не появляется — твоя версия Git Bash плохо работает с psql. Выполни `winpty psql -X` или открой в VS Code терминал PowerShell.

Проверь, куда попал:

```text
\conninfo
```

Строки, которые начинаются с `\`, — команды самого psql, точка с запятой им не нужна. А это уже SQL:

```sql
SELECT current_database(), current_user, version();
```

Видишь `;` в конце? SQL-команда заканчивается точкой с запятой. Без неё psql решит, что ты ещё не дописал, и сменит приглашение на `=>` с дефисом: `->`. Допиши `;` и нажми Enter.

Ещё два удобства на всю сессию:

```text
\pset pager off
\pset null '(пусто)'
```

Первое — показывать длинные результаты сразу, без пролистывания. Второе — показывать «пустые» значения явно. Выйти из psql — `\q`.

## Шаг 3. Проектируем

Посмотри на одну игру из `catalog.json` и подумай, как её разложить по таблицам:

```json
{ "id": 3, "title": "Neon Circuit", "genre": "Гонки", "price": 1499, "tags": ["киберпанк", "скорость", "мультиплеер"] }
```

**Жанр — отдельная таблица.** Если хранить жанр строкой в каждой игре, слово «Гонки» повторится у всех гонок. Однажды кто-нибудь напишет «гонки» или «Гонкии» — и фильтр на витрине сломается. Поэтому заводим таблицу `genres`, где каждый жанр записан **один раз**, а игра хранит только **номер** своего жанра — `genre_id`. Переименовать жанр — поменять одну строку, а не сто.

**Теги — сложнее.** У игры много тегов, и у тега много игр: «скорость» есть у трёх игр. Это связь **«многие ко многим»**. Хранить список в одном столбце `tags = 'киберпанк, скорость'` нельзя: такой текст не найдёшь по отдельному тегу и не проверишь на опечатки. Решение — третья, **связующая** таблица `game_tags`: каждая строка в ней — одна пара «игра — тег». У Neon Circuit три тега — три строки.

Получилась схема:

![Схема базы каталога](/materials/mediahub/assets/diagrams/lab17-er.svg)

- **Первичный ключ** (primary key, 🔑) — столбец, который однозначно определяет строку. У нас это `id`: номер, который база выдаёт сама.
- **Внешний ключ** (foreign key, 🔗) — столбец, который ссылается на первичный ключ другой таблицы. `games.genre_id` указывает на `genres.id`. База гарантирует, что ссылка ведёт на существующую строку.
- **«1 — ∞»** на схеме — «один ко многим»: в одном жанре много игр, у игры ровно один жанр.

## Шаг 4. Таблицы

Создай в проекте папку `db` и в ней файл `01_schema.sql`:

```sql
-- PixelPort: каталог игр. Скрипт можно запускать повторно:
-- он удаляет старые таблицы и создаёт их заново.
DROP TABLE IF EXISTS game_tags, games, tags, genres;

CREATE TABLE genres (
    id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL UNIQUE
);

CREATE TABLE tags (
    id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL UNIQUE
);

CREATE TABLE games (
    id               integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    slug             text    NOT NULL UNIQUE,
    title            text    NOT NULL,
    genre_id         integer NOT NULL REFERENCES genres (id),
    developer        text    NOT NULL,
    release_year     integer NOT NULL CHECK (release_year BETWEEN 1970 AND 2100),
    price            integer NOT NULL CHECK (price >= 0),
    discount_percent integer NOT NULL DEFAULT 0 CHECK (discount_percent BETWEEN 0 AND 90),
    rating           integer NOT NULL CHECK (rating BETWEEN 0 AND 100),
    description      text    NOT NULL
);

-- Связь «многие ко многим»: у игры много тегов, у тега много игр
CREATE TABLE game_tags (
    game_id integer NOT NULL REFERENCES games (id) ON DELETE CASCADE,
    tag_id  integer NOT NULL REFERENCES tags (id),
    PRIMARY KEY (game_id, tag_id)
);
```

Разберём, что тут написано. Каждая строчка — правило, которое база будет охранять сама:

| Запись | Что значит |
| --- | --- |
| `integer`, `text` | Типы: целое число и строка любой длины |
| `GENERATED ALWAYS AS IDENTITY` | Номер выдаёт база: 1, 2, 3… Вручную задать нельзя |
| `PRIMARY KEY` | Первичный ключ: уникален и не пуст |
| `NOT NULL` | Значение обязательно |
| `UNIQUE` | Повторяться не может: два жанра «Гонки» не создать |
| `REFERENCES genres (id)` | Внешний ключ: только номер существующего жанра |
| `CHECK (…)` | Любое условие: цена не отрицательная, скидка от 0 до 90 |
| `DEFAULT 0` | Значение, если при добавлении не указали |
| `ON DELETE CASCADE` | Удалили игру — её строки в `game_tags` удалятся сами |
| `PRIMARY KEY (game_id, tag_id)` | Ключ из двух столбцов: одна и та же пара не повторится |

Имена — маленькими буквами через подчёркивание (`discount_percent`), так принято в PostgreSQL. Сравни с `discountPercent` в TypeScript и `DiscountPercent` в C#: у каждого языка свои привычки, и мостики между ними — одна из задач интеграции.

**Порядок важен.** `games` ссылается на `genres`, поэтому `genres` создаётся раньше. А `DROP` в начале перечисляет таблицы так, чтобы ссылающиеся удалялись первыми.

Выполни файл в psql:

```text
\i db/01_schema.sql
```

`\i` — «выполни команды из файла». Путь отсчитывается от папки, где ты запустил psql, — от корня проекта. При первом запуске будут сообщения `NOTICE: table "game_tags" does not exist, skipping` — это `DROP IF EXISTS` честно говорит, что удалять пока нечего.

Посмотри, что получилось:

```text
\dt
\d games
```

`\dt` — список таблиц, `\d games` — устройство таблицы: столбцы, типы, а внизу все ограничения с именами, которые база придумала сама: `games_discount_percent_check`, `games_slug_key`, `games_genre_id_fkey`. Эти имена ты скоро увидишь в ошибках.

     'Побеждайте на ночных трассах футуристического города.'),

**Связи по именам.** Для `game_tags` нужны пары номеров. В файле они записаны понятными именами, а номера подставляет `JOIN` — о нём в шаге 7, пока просто прочитай.

```text
\i db/02_data.sql
```

Проверь, что всё на месте:

```sql
SELECT COUNT(*) FROM games;      -- 12
SELECT COUNT(*) FROM genres;     -- 8
SELECT COUNT(*) FROM tags;       -- 22
SELECT COUNT(*) FROM game_tags;  -- 35
```

## Шаг 6. Спрашиваем базу

Попробуй прямо в psql. Это основа SQL — **SELECT**, «выбери»:

```sql
SELECT title, price FROM games;
```

Добавим условие и порядок:

```sql
SELECT title, price, discount_percent
FROM games
WHERE discount_percent > 0
ORDER BY discount_percent DESC;
```

`WHERE` — фильтр (как `filter` в TypeScript и `Where` в LINQ), `ORDER BY … DESC` — сортировка по убыванию. Столбцы можно не только брать, но и вычислять:

```sql
SELECT title,
       price * (100 - discount_percent) / 100 AS final_price
FROM games
ORDER BY final_price
LIMIT 3;
```

`AS` даёт вычисленному столбцу имя, `LIMIT 3` — только первые три строки. Деление целых чисел в PostgreSQL, как и в C#, отбрасывает дробную часть — цены совпадут с сайтом. Первой будет Cloud Bakery за 349.

Знакомая картина? Это те же операции, что `selectGames` в №09 и цепочка `Where`/`OrderBy` в №15. Только теперь их выполняет база — там, где лежат данные.

## Шаг 7. JOIN и GROUP BY

**JOIN — склеить таблицы.** В `games` у Neon Circuit записано `genre_id = 2`. Человеку нужно слово «Гонки». Его надо взять из `genres`:

```sql
SELECT games.title, genres.name AS genre
FROM games
JOIN genres ON genres.id = games.genre_id;
```

`JOIN genres ON …` — «приставь к каждой игре строку жанра, у которой `id` равен `genre_id` игры». Когда в запросе несколько таблиц, столбцы называют с именем таблицы: `games.title`, `genres.name`.

Для тегов нужна цепочка из трёх таблиц: игра → её строки в `game_tags` → теги:

```sql
SELECT games.title, tags.name AS tag
FROM games
JOIN game_tags ON game_tags.game_id = games.id
JOIN tags ON tags.id = game_tags.tag_id
WHERE games.slug = 'neon-circuit';
```

Три строки: киберпанк, скорость, мультиплеер. Теперь перечитай последний `INSERT` в `02_data.sql` — он устроен так же.

**GROUP BY — посчитать по группам.** Сколько игр в каждом жанре?

```sql
SELECT genres.name AS genre, COUNT(*) AS games_count
FROM games
JOIN genres ON genres.id = games.genre_id
GROUP BY genres.name
ORDER BY games_count DESC;
```

`GROUP BY` раскладывает строки по кучкам с одинаковым жанром — точно как `GroupBy` в эндпоинте `/api/genres` из №15. **Агрегатная функция** считает по каждой кучке одно число: `COUNT(*)` — сколько строк, `SUM`, `AVG`, `MIN`, `MAX` — сумма, среднее, минимум, максимум.

## Шаг 8. Пять вопросов аналитика

Лёша прислал вопросы. Создай `db/03_reports.sql` и напиши в нём пять запросов, каждый с комментарием-заголовком. Проверяй каждый в psql (`\i db/03_reports.sql` выполнит все сразу).

**Отчёт 1. Три самые дорогие игры — по цене, которую реально заплатит покупатель.** Нужны: название, цена, скидка, цена со скидкой.

> Проверка: Orbital Echo 1299, Iron Harbor 1199, Hollow Bell 1099. Обрати внимание: Neon Circuit дороже всех «на ценнике», но со скидкой 60% в тройку не попадает.

**Отчёт 2. Средняя скидка по жанрам.** Жанр, сколько в нём игр, средняя скидка с одним знаком после запятой. Сначала жанры с самой большой скидкой.

> Подсказка: `ROUND(AVG(…), 1)`. Проверка: первые строки — Симуляторы 1 50.0, Гонки 2 42.5.

**Отчёт 3. Популярные теги.** Теги, которые есть хотя бы у двух игр, и у скольких игр каждый. Сначала самые популярные.

> Подсказка: условие на результат группировки пишется не в `WHERE`, а в `HAVING COUNT(*) >= 2` после `GROUP BY`. Проверка: 10 тегов, первый — атмосфера 4, второй — скорость 3.

**Отчёт 4. Игры для любителей атмосферы.** Название, жанр и рейтинг игр с тегом «атмосфера», от лучших к худшим.

> Подсказка: четыре таблицы в одном запросе. Проверка: Lantern Valley, Polar Signal, Mossbound, Hollow Bell.

**Отчёт 5. Теги одной строкой.** Для каждой игры — название и все её теги через запятую по алфавиту, например `киберпанк, мультиплеер, скорость`. Игры по порядку `id`.

> Подсказка: агрегатная функция `STRING_AGG(tags.name, ', ' ORDER BY tags.name)` склеивает строки группы в одну. Проверка: 12 строк, у Orbital Echo — `исследование, космос, сюжет`.

Этот отчёт — то, что понадобится сайту: карточка игры со списком тегов. В №18 такой же результат даст LINQ.

## 🔧 Сломай нарочно

База обещала охранять правила — проверим. Все команды выполняй в psql.

**Опыт 1. Скидка 95%.**

```sql
UPDATE games SET discount_percent = 95 WHERE slug = 'neon-circuit';
```

```text
ERROR:  new row for relation "games" violates check constraint "games_discount_percent_check"
DETAIL:  Failing row contains (3, neon-circuit, Neon Circuit, 2, Prism Drive, 2025, 1499, 95, 95, …).
```

`UPDATE … SET` меняет значения в строках, которые подходят под `WHERE`. Но `CHECK` не пустил. Обрати внимание: ошибка называет ограничение по имени — то самое из `\d games`. Если у тебя сообщения по-русски («новая строка в отношении "games" нарушает ограничение-проверку…»), значит сервер установлен с русским языком сообщений — суть та же.

**Опыт 2. Двойник.** Попробуй добавить игру с уже занятым адресом:

```sql
INSERT INTO games (slug, title, genre_id, developer, release_year, price, rating, description)
VALUES ('neon-circuit', 'Neon Circuit 2', 2, 'Prism Drive', 2026, 1999, 0, 'Сиквел');
```

```text
ERROR:  duplicate key value violates unique constraint "games_slug_key"
DETAIL:  Key (slug)=(neon-circuit) already exists.
```

Страница `game.html` скоро будет искать игру по `slug`. Два одинаковых — и непонятно, какую показывать. `UNIQUE` этого не допустит.

**Опыт 3. Жанр, в котором есть игры.**

```sql
DELETE FROM genres WHERE name = 'Хоррор';
```

```text
ERROR:  update or delete on table "genres" violates foreign key constraint "games_genre_id_fkey" on table "games"
DETAIL:  Key (id)=(5) is still referenced from table "games".
```

Hollow Bell осталась бы с жанром, которого нет. Внешний ключ защищает ссылку с обеих сторон: нельзя сослаться на несуществующий жанр и нельзя удалить жанр, на который ссылаются. Попробуй сам первое: вставь игру с `genre_id` равным 99.

**Опыт 4. Каскад — и отмена.** Удалим игру, но так, чтобы можно было передумать:

```sql
BEGIN;
DELETE FROM games WHERE slug = 'hollow-bell';
SELECT COUNT(*) FROM game_tags;
ROLLBACK;
SELECT COUNT(*) FROM game_tags;
```

После удаления в `game_tags` 32 строки: три тега Hollow Bell удалились сами — это `ON DELETE CASCADE`. А после `ROLLBACK` снова 35, и игра на месте. `BEGIN` начинает **транзакцию** — пачку изменений, которая либо применится вся (`COMMIT`), либо отменится вся (`ROLLBACK`). В №22 на транзакции будет держаться покупка.

**Опыт 5. Что считать?** Забудь `GROUP BY`:

```sql
SELECT genres.name, COUNT(*) FROM games JOIN genres ON genres.id = games.genre_id;
```

```text
ERROR:  column "genres.name" must appear in the GROUP BY clause or be used in an aggregate function
```

`COUNT(*)` сворачивает все строки в одно число, а `genres.name` — у каждой строки свой. Какое имя показать рядом с единственным числом? База не гадает, а честно отказывается. Добавь `GROUP BY genres.name` — и всё встанет на место.

После опытов перезапусти оба скрипта (`\i db/01_schema.sql`, потом `\i db/02_data.sql`) — база вернётся к исходному виду. Вот зачем `DROP` в начале схемы.

## Дополнительные квесты

### ★★ Игры без тегов

Добавь игру без единого тега (придумай свою). Отчёт 5 её не покажет: обычный `JOIN` выбрасывает строки, которым не нашлась пара. Перепиши отчёт с `LEFT JOIN`, чтобы игра появилась с пустым списком тегов, и напиши запрос «игры без тегов» — подсказка: `WHERE tags.id IS NULL`. Не забудь удалить свою игру или пересоздать базу скриптами.

### ★★ Распродажа одной командой

Маркетинг решил: всем стратегиям скидка 25%, но тем, у кого скидка уже больше, оставить их скидку. Напиши один `UPDATE`, сделай его внутри `BEGIN`, проверь результат `SELECT`-ом и только потом `COMMIT`. Затем подумай, что будет, если поставить условие «всем играм +50% к текущей скидке» — и проверь в транзакции, как отреагирует `CHECK`.

### ★★★ Представление «Игры со скидкой»

Создай в `01_schema.sql` **представление** (VIEW) `games_on_sale`: игры со скидкой, с названием жанра, ценой, скидкой и ценой со скидкой, сортировка по размеру скидки. Представление — сохранённый запрос, к которому можно обращаться как к таблице: `SELECT * FROM games_on_sale;`. Проверь, что после `UPDATE` скидки у игры представление сразу показывает новые данные. Объясни на защите, чем представление отличается от таблицы и почему `DROP` в начале схемы теперь должен удалять и его.

## Шпаргалка

| Команда | Что делает |
| --- | --- |
| `psql -X` | Подключиться (параметры из `PGHOST`, `PGUSER`…) |
| `\conninfo`, `\dt`, `\d таблица` | Куда подключён / список таблиц / устройство таблицы |
| `\i файл.sql`, `\q` | Выполнить файл / выйти |
| `CREATE TABLE t (…)`, `DROP TABLE IF EXISTS t` | Создать / удалить таблицу |
| `PRIMARY KEY`, `REFERENCES t (id)` | Первичный / внешний ключ |
| `NOT NULL`, `UNIQUE`, `CHECK (…)`, `DEFAULT x` | Ограничения |
| `INSERT INTO t (a, b) VALUES (1, 'x')` | Добавить строку |
| `UPDATE t SET a = 1 WHERE …` | Изменить строки |
| `DELETE FROM t WHERE …` | Удалить строки |
| `SELECT … FROM … WHERE … ORDER BY … LIMIT n` | Выбрать |
| `JOIN t2 ON t2.id = t1.t2_id` | Склеить таблицы |
| `GROUP BY …`, `HAVING …` | Группировка / условие на группы |
| `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `STRING_AGG` | Агрегатные функции |
| `BEGIN` … `COMMIT` / `ROLLBACK` | Транзакция: применить / отменить всё |
