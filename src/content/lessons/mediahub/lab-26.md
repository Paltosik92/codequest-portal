> **Сегодня ты сделаешь:** впервые поработаешь над кодом **вдвоём**, как в настоящей команде. Каждый делает свою задачу в своей **ветке**, предлагает её в общий `main` через **pull request**, а сосед проверяет код на **ревью**. Задачи подобраны с подвохом: обе меняют одни и те же строки карточки игры. Когда первая задача попадёт в `main`, вторая упрётся в **конфликт** — и разрешить его нужно с умом, а не кнопкой «взять всё».

## Шаг 1. Как работают команды: GitHub Flow

До сих пор ты коммитил прямо в `main` — ты был один. В команде так нельзя: два человека, пишущие в `main` одновременно, постоянно ломают друг другу работу, а сайт собирается из полуготового кода. Поэтому почти все команды работают по простому правилу — **GitHub Flow** (схема в начале работы):

1. `main` всегда рабочий. С него собирается сайт.
2. Новая задача — новая **ветка** от `main`: `feature/короткое-название`.
3. Готово — открываешь **pull request** (запрос на слияние): «предлагаю влить мою ветку в `main`».
4. Коллега делает **ревью**: читает изменения, задаёт вопросы, одобряет.
5. Одобрено — PR вливается в `main` кнопкой на GitHub. Ветка удаляется.

**Ветка** — это просто подвижный указатель на коммит. Пока ты в ветке, твои коммиты не трогают `main`. В любой момент можно переключиться обратно.

## Шаг 3. Ветки и задачи

Каждый — в своей рабочей копии:

```bash
git switch main
git pull
git switch -c feature/new-badge       # студент 1
git switch -c feature/rating-words    # студент 2
```

`git switch -c` создаёт ветку и сразу переключается в неё. `git branch` покажет все ветки, текущая — со звёздочкой.

### Задача студента 1: «🆕 новинка»

В `src/render.ts` перед функцией `createGameCard` добавь:

```ts
// Новинки — игры этого года выпуска и новее
const NEW_RELEASE_YEAR = 2025;

export function isNewRelease(game: Game): boolean {
  return game.year >= NEW_RELEASE_YEAR;
}
```

В `createGameCard` строку `meta.textContent = …` замени на:

```ts
  const newMark = isNewRelease(game) ? " · 🆕 новинка" : "";
  meta.textContent = `${game.genre} · ${game.year}${newMark} · ${rating}`;
```

Собери и проверь: у Neon Circuit, Polar Signal, Hollow Bell, Skyline Strikers — «2025 · 🆕 новинка».

### Задача студента 2: оценка словами

В `src/render.ts` перед функцией `createGameCard` добавь:

```ts
// Оценка словами, как в больших магазинах
export function describeRating(rating: number | null): string {
  if (rating === null) {
    return "Пока нет отзывов";
  }
  if (rating >= 80) {
    return `👍 ${rating}% · очень положительные`;
  }
  if (rating >= 60) {
    return `👍 ${rating}% · в основном положительные`;
  }
  if (rating >= 40) {
    return `${rating}% · смешанные`;
  }
  return `👎 ${rating}% · в основном отрицательные`;
}
```

Оценка словами длинная, в строку с жанром она не влезет. Вынесем её в отдельную строку карточки. В `createGameCard` две строки

```ts
  const rating = game.rating === null ? "нет отзывов" : `👍 ${game.rating}%`;
  meta.textContent = `${game.genre} · ${game.year} · ${rating}`;
```

замени на:

```ts
  meta.textContent = `${game.genre} · ${game.year}`;

  const rating = document.createElement("p");
  rating.className = "card-rating";
  rating.textContent = describeRating(game.rating);
```

И в `card.append(…)` после `meta` добавь `rating`:

```ts
  card.append(wishButton, link, meta, rating, createPrice(game), buyButton);
```

В `styles.css` после правила `.card:hover` добавь:

```css
.card-rating {
  color: var(--color-text-muted);
  font-size: 14px;
}
```

Собери и проверь: под «Жанр · год» — строка «👍 97% · очень положительные».

### Оба: коммит и отправка ветки

```bash
npm run build
git add .
git commit -m "Mark new releases on game cards"         # студент 1
git commit -m "Describe game rating in words on cards"   # студент 2
git push -u origin feature/new-badge                     # студент 1
git push -u origin feature/rating-words                  # студент 2
```

`-u` запоминает связь: дальше в этой ветке хватит просто `git push`. В `main` вы оба ничего не меняли — проверь: `git log --oneline main -1` показывает тот же коммит, что был до работы.

## Шаг 4. Pull request

На странице репозитория появится жёлтая плашка «feature/… had recent pushes» → **Compare & pull request**. Если её нет — вкладка Pull requests → New pull request, base: `main`, compare: твоя ветка.

Заполни:

- **Заголовок** — что сделано, как сообщение коммита, но по-русски: «Пометка „новинка“ на карточках игр».
- **Описание:**

  ```markdown
  ## Что сделано
  На карточках игр 2025 года и новее — «🆕 новинка».

  ## Как проверить
  1. `npm run build`, Live Server, главная.
  2. У Neon Circuit, Polar Signal, Hollow Bell, Skyline Strikers — пометка, у остальных нет.

  Тикет: PIX-026
  ```

- **Reviewers** (справа) — сосед.

**Create pull request.** Посмотри вкладку **Files changed**: GitHub показывает разницу — зелёное добавлено, красное удалено. Это ровно то, что будет читать ревьюер.

## Шаг 5. Ревью

Открой PR **соседа** → Files changed. Читай как придирчивый, но доброжелательный коллега:

- Делает ли код то, что написано в описании? Проверь сам: `git fetch`, `git switch <ветка соседа>`, `npm run build`, Live Server. Потом вернись в свою ветку.
- Понятны ли имена? Нет ли лишнего: отладочного `console.log`, закомментированного кода, случайных файлов?
- Что будет в крайних случаях? Например, у игры нет отзывов, или вышла новая игра 2026 года.

Наведи на строку → синий **+** → оставь комментарий. Хотя бы один — вопрос или предложение по делу. «Норм» — не ревью. «Почему `NEW_RELEASE_YEAR` — константа, а не „текущий год минус один“? Через год все новинки перестанут быть новинками?» — ревью.

Закончи: **Review changes** →

- **Comment** — есть вопросы, но не блокируют;
- **Approve** — можно вливать;
- **Request changes** — надо исправить.

Если попросили исправить — автор делает ещё один коммит в **ту же ветку** и `git push`. PR обновится сам. Ответь на комментарий, нажми **Resolve conversation**.

## Шаг 6. Первый PR — в main

Вливаем по очереди: **сначала PR студента 1** (`feature/new-badge`). Когда он одобрен, студент 1 нажимает **Merge pull request** → **Confirm merge** → **Delete branch**.

Открой `main` на GitHub — в истории коммит «Merge pull request #1 from …». Через минуту-другую GitHub Pages пересоберёт сайт: новинки уже на `github.io`.

Теперь откройте PR студента 2. Внизу вместо зелёной кнопки:

```text
This branch has conflicts that must be resolved
Conflicting files: js/render.js  js/render.js.map  src/render.ts
```

Пока ветка студента 2 жила своей жизнью, `main` ушёл вперёд — и изменил те же строки.

## Шаг 7. Конфликт

**Конфликт** — это когда две ветки изменили одно и то же место по-разному, и git не может решить сам, что оставить. Это не ошибка и не авария: git честно говорит «тут нужен человек».

**Студент 2** подтягивает свежий `main` в свою ветку:

```bash
git switch main
git pull
git switch feature/rating-words
git merge main
```

```text
Auto-merging js/render.js
CONFLICT (content): Merge conflict in js/render.js
Auto-merging js/render.js.map
CONFLICT (content): Merge conflict in js/render.js.map
Auto-merging src/render.ts
CONFLICT (content): Merge conflict in src/render.ts
Automatic merge failed; fix conflicts and then commit the result.
```

Открой `src/render.ts`. Git вставил **маркеры**:

```text
<<<<<<< HEAD
  …как в твоей ветке…
=======
  …как в main…
>>>>>>> main
```

Конфликтов в файле **два**. Посмотри на каждый и подумай, чего хотела каждая сторона. Не жми «Accept Current» или «Accept Incoming», не подумав: каждая из них выбросит чужую работу.

**Конфликт 1 — новые функции.** Обе ветки добавили функцию в одно место: ты — `describeRating`, студент 1 — `NEW_RELEASE_YEAR` и `isNewRelease`. Нужны **обе**. Но присмотрись к фигурным скобкам: закрывающая `}` после маркеров одна на двоих. Каждой функции нужна своя.

**Конфликт 2 — строка жанра.** Тут не выбрать одну сторону:

- в твоей ветке рейтинг ушёл в отдельную строку, а в строке жанра остались жанр и год;
- в `main` к строке жанра добавилась «новинка» — и старый рейтинг.

Правильный результат — **смысл обеих сторон**: в строке жанра — жанр, год и «новинка», рейтинг — отдельной строкой, словами. Напиши это сам: три-пять строк, все детали у тебя перед глазами. Если не выходит — разбор ниже.

<details>
<summary>Как должно получиться</summary>

```ts
  const newMark = isNewRelease(game) ? " · 🆕 новинка" : "";
  meta.textContent = `${game.genre} · ${game.year}${newMark}`;

  const rating = document.createElement("p");
  rating.className = "card-rating";
  rating.textContent = describeRating(game.rating);
```

А между функциями `describeRating` и комментарием «Новинки…» — недостающая `}` и пустая строка.

</details>

**Собранные файлы `js/render.js` и `.map` руками не правят.** Их делает TypeScript: исправь исходник и собери заново — сборка перезапишет оба файла целиком, вместе с маркерами.

```bash
npm run build
```

Сборка без ошибок, в `src/render.ts` не осталось ни одного `<<<<<<<` (поиск в VS Code)? Проверь в Live Server: «новинка» на месте, оценка словами на месте. Тогда завершай слияние:

```bash
git add .
git commit
git push
```

`git commit` без `-m` откроет редактор с готовым сообщением «Merge branch 'main' into feature/rating-words» — сохрани и закрой. (Если открылся Vim: `Esc`, затем `:wq`, `Enter`.)

Вернись в PR студента 2: конфликтов нет, появился новый коммит слияния. **Студент 1**, посмотри ревью ещё раз — именно слияние: всё ли твоё на месте? Approve. Студент 2 — **Merge pull request** → Delete branch.

> ✅ **Проверь себя:**
> - На GitHub в Pull requests → Closed — два PR, оба «Merged», в каждом ревью с комментарием.
> - В `main` на GitHub: «Merge pull request #1…», «Merge pull request #2…».
> - Оба: `git switch main`, `git pull`, Live Server — новинки и оценка словами вместе.
> - Через пару минут то же на `github.io` студента 1.
> - Локальные ветки больше не нужны: `git branch -d feature/new-badge` (или `rating-words`).

## 🔧 Сломай нарочно

**Опыт 1. «Accept Both» не думая.** Сделай этот опыт **до** того, как разрешишь конфликт по-настоящему (или повтори слияние на копии ветки). В VS Code над каждым конфликтом нажми **Accept Both Changes** и запусти `npm run build`:

```text
src/render.ts(…): error TS1005: '}' expected.
```

Не хватает той самой скобки из конфликта 1. Допиши её и собери снова:

```text
error TS2451: Cannot redeclare block-scoped variable 'rating'.
```

В конфликте 2 «обе стороны» — это два разных `rating`: строка и элемент. Механическое «взять всё» дало код, который не компилируется. А если бы обе стороны случайно совместились без ошибки — дало бы код, который работает неправильно. Отмени слияние целиком и вернись к состоянию до `git merge`:

```bash
git merge --abort
```

`git merge --abort` — кнопка «как будто ничего не было», пока слияние не закоммичено. Теперь разреши конфликт как в шаге 7.

**Опыт 2. Устаревший `main`.** Сразу после шага 6 — PR #1 уже влит, а `git pull` из шага 7 ещё не сделан — **студент 2** переключись на `main`, поменяй что-нибудь безобидное (например, текст в подвале `index.html`), закоммить и `git push`:

```text
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/…/pixelport.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.
```

GitHub не даёт перезаписать чужую работу: в его `main` есть коммит, которого у тебя нет. Именно поэтому перед новой веткой всегда `git switch main` и `git pull`. Отмени свой коммит, он был лишним: `git reset --hard origin/main`. Осторожно: эта команда выбрасывает незакоммиченные изменения в рабочей папке.

## Дополнительные квесты

### ★ Шаблон pull request

Чтобы каждый PR начинался с правильных разделов, создай в репозитории файл `.github/pull_request_template.md` с заготовкой «Что сделано / Как проверить / Тикет». Сделай это **тоже через ветку и PR** — по-другому в `main` теперь не принято. Проверь: новый PR открывается уже с шаблоном.

### ★★ Защитить main

Сделай так, чтобы в `main` нельзя было отправить коммит напрямую. Студент 1: Settings → Branches → Add branch ruleset (или Add rule) для `main` → «Require a pull request before merging», одобрений: 1. Проверь опытом 2, только теперь со свежим `main` (`git pull` перед коммитом): у студента 2 `git push` в `main` всё равно отклоняется — с упоминанием правил ветки. Владельца репозитория классические правила по умолчанию пропускают (галочка «Do not allow bypassing…» это меняет), а ruleset — нет, если его нет в списке исключений. Защищённая ветка — правило, которое не держится на честном слове.

### ★★★ Поменяться ролями

Повторите всё в репозитории **студента 2** с теми же задачами, но наоборот: «новинку» делает студент 2, оценку словами — студент 1, а первым в `main` вливается PR **с оценкой**. Конфликт будет решать студент 1, и «HEAD» и «main» в маркерах поменяются местами. Заодно у обоих в репозиториях окажутся обе функции.

## Шпаргалка

| Команда / действие | Что делает |
| --- | --- |
| `git switch -c feature/x` | Создать ветку и перейти в неё |
| `git switch main` | Перейти в ветку `main` |
| `git branch`, `git branch -d x` | Список веток; удалить влитую ветку |
| `git push -u origin feature/x` | Отправить ветку и запомнить связь |
| `git pull` | Забрать и влить изменения с GitHub |
| `git fetch` | Только забрать, ничего не вливая |
| `git merge main` | Влить `main` в текущую ветку |
| `git merge --abort` | Отменить незаконченное слияние |
| `<<<<<<< HEAD … ======= … >>>>>>> main` | Конфликт: твоя версия, потом чужая |
| Compare & pull request | Открыть PR на GitHub |
| Files changed → **+** у строки | Комментарий к строке на ревью |
| Review changes → Approve | Одобрить PR |
| Merge pull request → Delete branch | Влить PR и удалить ветку |
