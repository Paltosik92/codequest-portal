## Шаг 2. Как выглядит хороший тикет

Вот пример — функции нет в меню, чтобы не было соблазна переписать. Читай не что сделано, а **как написано**.

```markdown
# PIX-100. Выбор редакции

**Автор:** Иван Иванов, ИС-31 · **Сложность:** ★★ · **Ветка:** `feature/editors-choice`
**Статус:** утверждён преподавателем

## История

Как **покупатель**, который не знает, во что поиграть, я хочу **видеть игры, которые советует сам магазин**, чтобы **быстрее выбрать что-то хорошее**.

Как **администратор**, я хочу **отмечать такие игры в админке**, чтобы **менять подборку без программиста**.

## Критерии приёмки

1. У игры из подборки на обложке — бейдж «★ Выбор редакции»: на витрине, в «Вам может понравиться» и на странице игры.
2. На витрине — флажок «Выбор редакции»: оставляет только игры подборки и работает вместе с остальными фильтрами. Без сервера (GitHub Pages) — тоже.
3. В админке у каждой игры — флажок «Выбор редакции». Щелчок сразу сохраняет на сервере; после перезагрузки страницы состояние то же. При ошибке сервера флажок возвращается в прежнее положение, и видно сообщение.
4. `PUT /api/games/999/editors-choice` → 404; запрос без поля `isEditorsChoice` → 400.
5. В новой базе подборка — Iron Harbor, Lantern Valley, Hollow Bell. В уже заполненной базе — те же три игры после миграции.
6. Отметка не меняет цену и порядок сортировки.

## Контракт API

| Запрос | Ответ |
| --- | --- |
| `GET /api/games?editorsChoice=true` | 200, только игры подборки; вместе с остальными параметрами |
| `GET /api/games`, `GET /api/games/{id}` | у каждой игры новое поле `isEditorsChoice: boolean` |
| `PUT /api/games/{id}/editors-choice`, тело `{ "isEditorsChoice": true }` | 200 и игра целиком; 400 — нет поля; 404 — нет игры |

## База данных

- Новый столбец `games.is_editors_choice boolean NOT NULL DEFAULT false`, миграция `AddEditorsChoice`.
- Данные: в новой базе подборку проставит сидер из поля `editorsChoice` в `catalog.json`; в уже заполненной — `UPDATE` внутри миграции. Без второго пути у всех, кто уже запускал проект, подборка окажется пустой.

## Риски и вопросы

- В левом верхнем углу обложки уже бейдж скидки, в правом — ♡. Новый бейдж — в левый нижний, чтобы не перекрывались.
- Без сервера админка не работает — менять подборку можно только с сервером, а показывать — в обоих режимах.
```

А вот макет из тикета — простая схема без красоты, но всё новое на ней видно:

На что обратить внимание:

- **История** отвечает на «кто, что, зачем». «Зачем» — польза пользователя, а не «потому что задали».
- **Критерии** проверяются за минуту, и ответ — «да» или «нет». Нет слов «удобно», «быстро», «красиво». Есть «плохие» случаи: 404, 400, ошибка сервера в админке, «после перезагрузки».
- **Контракт API** — точные адреса, тела и коды ответов. По нему можно писать фронтенд и сервер параллельно, как в №26.
- **База** — не только «добавить столбец», но и **откуда возьмутся данные** у тех, у кого база уже заполнена. Такие вещи обычно вспоминают слишком поздно.
- **План** идёт **снизу вверх**: база → сервер → фронтенд. Каждый шаг — коммит, и после каждого проект работает.
- **«Не входит»** — защита от разрастания: «а ещё можно было бы…» записывается туда, а не в код.

## Шаг 3. Напиши свой тикет

Создай ветку для своей функции и файл тикета:

```bash
git switch main
git pull
git switch -c feature/<короткое-имя>     # например feature/review-votes
mkdir -p docs
cp <путь к материалам>/feature-template.md docs/feature.md
```

Заполняй сверху вниз. В шаблоне в комментариях `<!-- … -->` — подсказки к каждому разделу. Когда раздел готов, подсказки удали.

Советы:

1. **Сначала критерии, потом всё остальное.** Критерии — это то, что ты покажешь на защите. Если не можешь написать критерий, значит, ещё не понял, что делаешь.
2. **Контракт — до кода.** Нарисуй запросы и ответы так, будто их уже кто-то сделал. Что вернёт сервер, если игрока нет? Если запрос повторили?
3. **Посмотри, что уже есть.** Подарок — это заказ с другим получателем (№22). История цен пишется там же, где меняется цена (№21). «Отзыв полезен» похож на отзывы (№19) и защиту от повторов (№22). Найди место в своём коде, куда встанет новое.
4. **Макет — от руки.** Сфотографируй и положи в `docs/` (например, `docs/feature-mockup.jpg`), поправь ссылку в тикете. Красота не нужна — нужно, чтобы было видно, **где** появится новое и что будет при ошибке.
5. **План — на две пары.** Сложи шаги. Если выходит больше — перенеси часть в «Не входит». Не наоборот.

## Шаг 4. Тикет на ревью

Закоммить тикет и выложи ветку:

```bash
git add docs
git commit -m "Add feature ticket for <функция>"
git push -u origin feature/<короткое-имя>
```

Открой pull request, но не обычный, а **черновик**: на кнопке «Create pull request» — стрелка ▾ → **Create draft pull request**. Черновик говорит всем: «Влить пока нельзя, но посмотрите». В описании — ссылка на `docs/feature.md` и одна фраза о функции.

**Ревью тикета соседа.** Сосед открывает **твой** репозиторий — в №26 вы уже соавторы, если нет — добавь. Он проверяет по списку и оставляет комментарии к строкам `docs/feature.md`:

- [ ] Понятно, **кто** пользователь и **зачем** ему это?
- [ ] Каждый критерий проверяется за минуту? Нет «удобно», «быстро», «красиво»?
- [ ] Есть хотя бы один «плохой» случай?
- [ ] У каждого запроса в контракте есть все ответы с кодами?
- [ ] Понятно, откуда возьмутся данные в уже заполненной базе?
- [ ] План помещается в две пары? Нет ли в нём того, что стоило бы перенести в «Не входит»?

Поправь тикет по комментариям — новым коммитом в ту же ветку — и ответь на каждый комментарий.

**Утверждение.** Позови преподавателя к своему черновику PR. Утверждённый тикет — это комментарий «Тикет утверждён» или Approve. После этого поменяй в тикете строку **Статус** на «утверждён преподавателем».

## Шаг 5. Начни снизу

Тикет утверждён — начинай реализацию **с первого шага плана**, обычно с базы данных:

- **Функция с базой:** класс-сущность или новое поле → настройка в `PixelPortDb` (ключи, индексы, ограничения) → `dotnet ef migrations add …` → загляни в созданный файл миграции → `dotnet ef database update` → проверь в psql `\d таблица`. Начальные данные — сидером и, если надо, `UPDATE` в миграции, как в примере.
- **Функция без базы:** начни с **формата данных** — интерфейс в `models.ts` и функции чтения/записи в `storage.ts`. Для «Цена снизилась» это главный вопрос: старое «Желаемое» лежит как массив чисел — что будет, когда новый код его прочитает?

Сделал шаг — проверь, что проект собирается и работает как раньше (`dotnet build`, `npm run build`, витрина открывается), закоммить и отправь:

```bash
git add .
git commit -m "Add review votes table"      # твоё сообщение — что сделано
git push
```

Черновик PR обновится сам. **Не вливай** его: функция ещё не готова. На №28 ты продолжишь в этой же ветке.

> ✅ **Проверь себя:**
> - В репозитории — ветка `feature/…` и черновик PR из неё.
> - В PR — файл `docs/feature.md` со статусом «утверждён», макет в `docs/`, комментарии соседа с твоими ответами.
> - После тикета в PR — хотя бы один коммит с кодом нижнего слоя; проект собирается.
> - `main` не тронут: `git log --oneline main -1` — тот же коммит, что после №26.
