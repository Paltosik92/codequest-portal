## Шаг 1. Чистый клон

Представь, что ты — директор с новым ноутбуком. Склонируй **свой** репозиторий в **новую** папку рядом с рабочей:

```bash
git clone https://github.com/<логин>/pixelport.git pixelport-clean
cd pixelport-clean
```

Открой в нём `README.md` и делай **ровно то, что написано**, — ни шагом больше. В `appsettings.json` клона укажи базу `pixelport_demo_<код>`. Это единственная правка; в git она не попадёт: в клоне ты ничего не коммитишь.

Заведи файл-блокнот (не в репозитории) и записывай **каждое** место, где:

- пришлось сделать что-то, чего нет в README;
- вылезла ошибка, и ты знал, как её обойти, а директор бы не знал;
- README говорит одно, а на деле по-другому: другие имена, порт, путь.

Скорее всего, ты наткнёшься хотя бы на одно из этого — в эталонном проекте курса на чистом клоне нашлись оба:

```text
error NETSDK1004: Assets file '…/server/obj/project.assets.json' not found. Run a NuGet package restore to generate this file.
Unable to retrieve project metadata. Ensure it's an SDK-style project.
```

— это `dotnet ef database update` в свежем клоне: проект ещё ни разу не собирался.

```text
Npgsql.PostgresException (0x80004005): 42P01: relation "games" does not exist
```

— это `dotnet run` до того, как применены миграции. Директор не поймёт, что от него хотят.

Дошёл до работающего магазина на `localhost:5080` — запиши, сколько минут это заняло. Это главная цифра релиза: сегодня её нужно уменьшить.

## Шаг 2. Исправь README

Вернись в **рабочую** папку (не в клон). Перепиши `README.md` так, чтобы по нему мог пройти человек без твоих знаний. Разделы:

1. **Что это** — одна-две фразы и скриншот главной (положи в `docs/`). Ссылка на `github.io` и честно: что там работает, что нет.
2. **Возможности** — по версиям: что появилось в 1.0 (твоя функция), 0.3, 0.2, 0.1.
3. **Технологии** — одна строка.
4. **Как запустить с сервером** — что установить заранее (Node.js, .NET SDK, PostgreSQL, пустая база), потом нумерованные шаги с командами **в том порядке, в котором они работают**. Где писать пароль и где не писать.
5. **Как запустить без сервера.**
6. **Частые проблемы** — таблица «сообщение → что делать». Впиши всё из своего блокнота и то, что видел за курс:

   | Сообщение | Причина и решение |
   | --- | --- |
   | `NETSDK1004: Assets file … not found` при `dotnet ef` | Проект не собран: `dotnet build`, потом снова `dotnet ef database update` |
   | `No password has been provided but the backend requires one` | Не задан пароль: `export PGPASSWORD='…'` в том же окне терминала |
   | `28P01: password authentication failed for user …` | Неверный пароль или пользователь в `appsettings.json` |
   | `Failed to bind to address http://127.0.0.1:5080: address already in use` | Сервер уже запущен в другом окне |

7. **Устройство проекта** — какая папка за что отвечает.
8. **API** — таблица запросов коротко; подробно — `pixelport.http`.
9. **Ограничения** — что учебное и не годится для настоящего магазина (вход, права на админку).

Пиши для директора: команды целиком, без «ну там настрой базу».

## Шаг 3. Понятная ошибка вместо падения

README читают не все. Пусть сервер сам подскажет, если база отстаёт от кода. Требование:

> При запуске сервер проверяет, применены ли все миграции. Если нет — пишет в лог (уровень `Critical`) список неприменённых миграций и команду, которая это исправит, и завершает работу, не трогая базу. Если всё применено — работает как раньше.

Подсказка: у `db.Database` есть метод `GetPendingMigrations()`. Проверку ставь в `Program.cs` **до** сидеров — сидеры первыми лезут в таблицы. Как завершить программу из `Program.cs` без исключения — подумай, что делает `return` в программе верхнего уровня.

Проверь на демо-базе: откати её (`dotnet ef database update 0`), запусти `dotnet run` — понятное сообщение. Примени одну старую миграцию (`dotnet ef database update <имя>`), запусти — в сообщении только недостающие миграции. Примени все — магазин работает.

Добавь эту ошибку в «Частые проблемы» README.

## 🔧 Сломай нарочно

**Опыт 1. Пароль, который не удалить.** Сделай во **временной** папке — не в проекте:

```bash
mkdir secret-test && cd secret-test && git init
echo '{ "ConnectionStrings": { "Db": "Host=localhost;Password=qwerty123" } }' > appsettings.json
git add . && git commit -m "Add settings"
git rm appsettings.json && git commit -m "Remove settings"
git log -p -S "qwerty123"
```

Файла нет, а пароль — в истории, его увидит любой, кто склонирует репозиторий. «Удалить коммитом» нельзя; убрать из истории можно, но сложно, а копии у всех, кто успел клонировать, останутся. Правильное действие при утечке — **сменить пароль**. Поэтому с №18 пароль живёт в `PGPASSWORD`, а не в файле. Удали папку `secret-test`.

**Опыт 2. Директор забыл миграции.** Очисти демо-базу и запусти сервер **без** `dotnet ef database update` — сначала на коде до шага 3 (если ещё не сделал), потом после. Сравни, что увидит человек в терминале. Хорошее сообщение об ошибке говорит не «что сломалось», а «что сделать».

**Опыт 3. Чужими глазами.** Попроси соседа открыть твой `github.io` с телефона и назвать первое, что непонятно или не работает. Без объяснений с твоей стороны. Запиши в чек-лист, что исправил.
