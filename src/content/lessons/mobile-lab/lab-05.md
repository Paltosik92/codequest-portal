**Дисциплина:** «Разработка мобильных приложений».
**Начало:** ваш GameBox после полностью выполненной ПР4.

Крестики-нолики готовы: можно играть вдвоём или против компьютера, а имя и результаты сохраняются. Бит возвращается на полку и открывает вторую карточку — «Змейка». Пока она умеет только сообщать о будущей игре.

«Теперь понадобится время», — замечает Бит. В крестиках-ноликах изменение начиналось с нажатия. Здесь голова должна переходить в соседнюю клетку через одинаковые интервалы, даже если игрок ничего не нажимает.

Сегодня оживим змейку из трёх сегментов. Сначала разберём один шаг руками, затем поручим его повторение единственному таймеру экрана. Управление и остановку проверим до того, как добавлять новые игровые правила.

![Бит возвращается из крестиков-ноликов на полку и открывает змейку, движение которой потребует игрового времени](/materials/mobile-lab/img/lab5/comic-01-snake-card-awakes.webp)

_Вторую карточку подключили ещё в ПР1. Теперь заменим её заглушку содержательной игрой в том же приложении._

## Результат занятия

После обязательной части:

- поле содержит ровно 16 строк и 16 столбцов;
- стартовое тело состоит из трёх клеток: `(8, 8)`, `(8, 7)`, `(8, 6)`;
- первый элемент списка — голова, последний — хвост;
- «Старт» включает движение вправо с постоянной длиной;
- один тик перемещает голову ровно в соседнюю клетку;
- экранные стрелки запрашивают направление следующего шага;
- разворот на противоположное направление запрещён;
- между тиками принимается максимум один осмысленный поворот;
- повторный «Старт» не создаёт второй таймер;
- выход, сворачивание и сброс останавливают прежний таймер;
- после фоновой паузы требуется явное продолжение;
- у края движение останавливается до записи недопустимой координаты;
- «В начало» возвращает три стартовых сегмента и ожидание запуска.

**Это версия движения с постоянной длиной.** Еды, роста, очков, рекорда, изменения темпа, свайпов и полноценного Game Over пока нет. Столкновение с собственным телом в этой работе ещё не определяет проигрыш.

До ПР7 у края показываем диагностику: **«Край поля — движение остановлено»**. В ПР7 это станет полноценным проигрышем. Прохода сквозь стену и появления с противоположной стороны нет.

_Точка отличает голову от тела не только цветом. Координаты под полем помогают проверить порядок списка; внутри 256 клеток текст не печатается._

## Как работать с методичкой

Продолжаем свой **конец ПР4**, а не исходную оболочку ПР1. Сохранённые результаты крестиков-ноликов и настройки имени должны остаться на месте.

Пути `lib/...` относятся к корню вашего Flutter-проекта с `pubspec.yaml`. Пути `img/lab5/...` относятся только к методичке: изображения не добавляются в `assets` приложения. Если будущие PNG отсутствуют, вся обязательная информация есть в тексте.

Готовую вёрстку, координаты и жизненный цикл копируйте. Самостоятельная часть небольшая: одно смещение, удаление хвоста и одно условие буфера направления по образцу.

Сначала соберём модель и экран с кнопкой **«Один шаг»**, чтобы наблюдать список без спешки. Затем заменим ручной вызов на **«Старт»** и один `Timer.periodic`. Ручная кнопка — промежуточная проверка, в итоговом экране её не оставляем.

### 1.3. Что означает движение

Один тик — один вызов `step()`. Он не означает кадр анимации: между тиками Flutter может перерисовать экран несколько раз, но тело не должно сделать лишний шаг.

У сегодняшнего тела всегда три сегмента. На обычном шаге добавляется одна новая голова и удаляется один хвост. Если новая голова вышла бы за поле, список вообще не меняется.

## 2. Подключаем координату GridPosition

### 2.1. Строка вниз, столбец вправо

Поле 16×16 содержит 256 клеток. Координата записывается **`(row, col)`**, именно в таком порядке.

| Координата      | Допустимые значения | При увеличении  |
| --------------- | ------------------- | --------------- |
| `row` — строка  | 0…15                | Движемся вниз   |
| `col` — столбец | 0…15                | Движемся вправо |

Верхний левый угол — `(0, 0)`, нижний правый — `(15, 15)`. Координата `(16, 8)` уже вне поля: число 16 задаёт количество строк, а не последний индекс.

| Направление | Изменение row | Изменение col | Пример из (8, 8) |
| ----------- | ------------: | ------------: | ---------------- |
| `up`        |            −1 |             0 | (7, 8)           |
| `down`      |            +1 |             0 | (9, 8)           |
| `left`      |             0 |            −1 | (8, 7)           |
| `right`     |             0 |            +1 | (8, 9)           |

![На поле 16 на 16 строка растёт вниз, столбец вправо, а четыре направления меняют только одну координату](/materials/mobile-lab/img/lab5/schema-01-coordinates.webp)

_Не переносим сюда привычку «ось Y вверх»: строки экрана нумеруются сверху вниз._

### 2.2. Готовый объект координаты

Создайте **`lib/core/grid_position.dart`** и вставьте код целиком:

```dart
class GridPosition {
  const GridPosition(this.row, this.col);

  final int row;
  final int col;

  GridPosition shifted(int deltaRow, int deltaCol) {
    return GridPosition(row + deltaRow, col + deltaCol);
  }

  @override
  bool operator ==(Object other) {
    return other is GridPosition && row == other.row && col == other.col;
  }

  @override
  int get hashCode => Object.hash(row, col);

  @override
  String toString() => '($row, $col)';
}
```

Это готовая инфраструктура. Вход — два целых числа. `shifted` возвращает новую координату со смещением и не изменяет старую; поля `final`.

Главная мысль: два разных объекта `GridPosition(4, 7)` обозначают одну клетку и должны сравниваться как равные. Поэтому `snake.contains(GridPosition(row, col))` найдёт сегмент по координатам, даже если экран создал новый объект для проверки.

`hashCode` согласован с тем же равенством для коллекций наподобие `Set`. Нам не нужно вычислять его вручную или сохранять между запусками. `toString` пригодится для короткой диагностической подписи списка.

Не добавляйте сюда `Timer`, состояние партии, Flutter или рисование клетки. Координата не знает, кто ею пользуется.

## 3. Разбираем и дополняем один шаг модели

### 3.1. Голова в начале, хвост в конце

Стартовое тело движется вправо:

```text
Список: [(8,8), (8,7), (8,6)]
Индекс:    0       1       2
Роль:   голова   тело    хвост

На поле слева направо: хвост (8,6) — тело (8,7) — голова (8,8) →
```

Порядок элементов списка не обязан совпадать с чтением рисунка слева направо. Мы храним путь **от головы к хвосту**, чтобы новая голова всегда добавлялась в начало.

### 3.2. Обязательный ручной эксперимент со списком

Пока не запускаем таймер. Запишите три строки или выложите три бумажные клетки.

Исходное состояние:

```text
[(8,8), (8,7), (8,6)]
direction = right
```

Сначала предскажите новую голову. Вправо увеличивается только `col`, поэтому это `(8, 9)`.

Добавили её **в начало**:

```text
[(8,9), (8,8), (8,7), (8,6)]
```

Это промежуточный список из четырёх элементов внутри одного метода, не готовый новый кадр. Теперь удалили последний элемент `(8, 6)`:

```text
[(8,9), (8,8), (8,7)]
```

Обычный шаг завершён: длина снова 3. Старое тело не передвигается отдельным циклом по каждому сегменту; нужный порядок получился добавлением и удалением.

![Новая голова добавляется в начало списка, старый хвост удаляется с конца, и после полного шага остаются три сегмента](/materials/mobile-lab/img/lab5/schema-03-head-and-tail.webp)

_Кадр обновим после всего шага, поэтому промежуточная длина 4 не появляется как отдельное состояние игры на экране._

### 3.3. Создаём модель почти целиком

Создайте **`lib/games/snake/snake_game.dart`** и вставьте:

```dart
import '../../core/grid_position.dart';

enum Direction { up, down, left, right }

enum SnakePhase { ready, running, paused, edgeStopped }

class SnakeGame {
  static const int size = 16;
  static const List<GridPosition> _initialSnake = [
    GridPosition(8, 8),
    GridPosition(8, 7),
    GridPosition(8, 6),
  ];

  final List<GridPosition> snake = List<GridPosition>.of(_initialSnake);
  Direction direction = Direction.right;
  Direction requestedDirection = Direction.right;
  SnakePhase phase = SnakePhase.ready;

  bool start() {
    if (phase == SnakePhase.running || phase == SnakePhase.edgeStopped) {
      return false;
    }
    phase = SnakePhase.running;
    return true;
  }

  void pause() {
    if (phase != SnakePhase.running) return;
    phase = SnakePhase.paused;
    requestedDirection = direction;
  }

  bool requestDirection(Direction next) {
    if (phase != SnakePhase.running || next == direction) return false;
    if (_isOpposite(direction, next)) return false;
    // Ограничение второго поворота добавим на этапе 6.
    requestedDirection = next;
    return true;
  }

  bool _isOpposite(Direction first, Direction second) {
    return (first == Direction.up && second == Direction.down) ||
        (first == Direction.down && second == Direction.up) ||
        (first == Direction.left && second == Direction.right) ||
        (first == Direction.right && second == Direction.left);
  }

  GridPosition _nextHead(Direction next) {
    final head = snake.first;
    switch (next) {
      case Direction.up:
        // Замените следующую строку по разделу 3.4.
        return head;
      case Direction.down:
        return head.shifted(1, 0);
      case Direction.left:
        return head.shifted(0, -1);
      case Direction.right:
        return head.shifted(0, 1);
    }
  }

  bool _inside(GridPosition position) {
    return position.row >= 0 && position.row < size &&
        position.col >= 0 && position.col < size;
  }

  bool step() {
    if (phase != SnakePhase.running) return false;
    final next = requestedDirection;
    final newHead = _nextHead(next);
    if (!_inside(newHead)) {
      phase = SnakePhase.edgeStopped;
      requestedDirection = direction;
      return false;
    }

    direction = next;
    snake.insert(0, newHead);
    // Удалите хвост по разделу 3.5.
    requestedDirection = direction;
    return true;
  }

  void reset() {
    snake
      ..clear()
      ..addAll(_initialSnake);
    direction = Direction.right;
    requestedDirection = Direction.right;
    phase = SnakePhase.ready;
  }
}
```

Сначала заполните **оба** учебных места ниже. Не запускайте движение с `return head` или без удаления хвоста.

В модели нет таймера и импорта Flutter. `start()` только меняет фазу: от этого сам по себе ни один шаг не произойдёт. Решение о времени вызова `step()` принадлежит экрану.

### 3.4. Самостоятельная часть: смещение вверх

В `_nextHead`, в ветке `Direction.up`, замените комментарий и следующий `return head;` правильным смещением. По образцу остальных веток меняется row на −1, col остаётся прежним.

**Подсказка:** первый параметр `shifted` — изменение строки.

Готовая строка для восстановления:

```dart
        return head.shifted(-1, 0);
```

Не возвращайте `shifted(0, -1)`: это движение влево. Не меняйте исходную голову через присваивание её полям — они неизменяемые.

### 3.5. Самостоятельная часть: удалить хвост

В `step` замените комментарий `// Удалите хвост по разделу 3.5.` одной операцией удаления **последнего** элемента `snake`.

**Подсказка:** метод называется `removeLast`. Не используйте `removeAt(0)`: нулевой элемент только что стал новой головой.

Готовая строка для восстановления:

```dart
    snake.removeLast();
```

Теперь обычный шаг содержит знакомую пару: `snake.insert(0, newHead);` → `snake.removeLast();`.

### 3.6. Фазы и граница поля

| Фаза          | Что происходит                         | Можно ли выполнить step |
| ------------- | -------------------------------------- | ----------------------- |
| `ready`       | Три стартовых сегмента, ждём кнопку    | Нет                     |
| `running`     | Экран разрешил движение                | Да                      |
| `paused`      | Положение сохранено, продолжение явное | Нет                     |
| `edgeStopped` | Следующая голова вышла бы за поле      | Нет; сначала «В начало» |

В `_inside` проверяются обе границы для обеих координат. Отказ происходит **до `insert`**, поэтому на поле не появляется сегмент с row или col равным −1 или 16.

Возвращаемый `bool` метода `step` сообщает, переместилось ли тело. `false` у края всё же сопровождается изменением фазы, поэтому экран должен показать новый статус.

`direction` меняется только при принятом шаге. До первого шага это стартовое направление; дальше — направление последнего успешного перемещения. `requestedDirection` ждёт следующего шага и не двигает тело само по себе.

Сохраните оба файла. Выполните `flutter analyze`: модель должна компилироваться, старый GameBox пока открывает прежнюю заглушку. Это ожидаемо до следующего этапа.

## Проверяем

1. Ручной прогноз дал `(8,9), (8,8), (8,7)`.
2. Вверх уменьшает row; вправо увеличивает col.
3. После `insert` удаляется последний сегмент.
4. Проверка границ стоит до изменения списка.
5. Модель не создаёт таймер и не рисует UI.

**Контрольная точка:** один шаг описан. Проверим его через экранную кнопку, пока без автоматического повторения.

## 4. Показываем поле и выполняем ручной шаг

### 4.1. Полностью заменяем заглушку

Откройте **`lib/games/snake/snake_screen.dart`** и замените файл целиком следующим кодом:

```dart
import 'dart:async';

import 'package:flutter/material.dart';

import '../../core/grid_position.dart';
import 'snake_game.dart';

class SnakeScreen extends StatefulWidget {
  const SnakeScreen({super.key});

  @override
  State<SnakeScreen> createState() => _SnakeScreenState();
}

class _SnakeScreenState extends State<SnakeScreen> {
  final SnakeGame _game = SnakeGame();
  Timer? _timer;
  late final AppLifecycleListener _lifecycle;
  bool _leaving = false;

  @override
  void initState() {
    super.initState();
    _lifecycle = AppLifecycleListener(onInactive: _pauseMovement);
  }

  String get _statusText {
    return switch (_game.phase) {
      SnakePhase.ready => 'Готова к запуску',
      SnakePhase.running => 'Движение',
      SnakePhase.paused => 'Пауза',
      SnakePhase.edgeStopped => 'Край поля — движение остановлено',
    };
  }

  void _stepOnce() {
    if (_leaving || !_game.start()) return;
    _game.step();
    _game.pause();
    setState(() {});
  }

  void _cancelTimer() {
    _timer?.cancel();
    _timer = null;
  }

  void _pauseMovement() {
    if (!mounted || _leaving || _game.phase != SnakePhase.running) return;
    _cancelTimer();
    _game.pause();
    setState(() {});
  }

  void _resetGame() {
```

### 4.2. Как индекс превращается в клетку

## 5. Подключаем один Timer.periodic

### 5.1. Кто отвечает за время

Теперь экран будет повторять **тот же** `step`, который только что вызвала ручная кнопка. Новый алгоритм движения для таймера не нужен.

```text
Старт → один Timer.periodic
каждые 400 мс → game.step()
→ setState → новое положение на экране
```

400 мс — фиксированный учебный интервал этой версии, без настройки и ускорения. Не требуется идеально точная частота: важно, что один вызов обработчика делает один дискретный шаг.

`setState` сам змейку не перемещает. Он сообщает Flutter, что данные модели изменились и экран нужно перестроить.

![Единственный таймер экрана вызывает шаг чистой модели, после чего setState показывает новое положение, а выход и пауза отменяют таймер](/materials/mobile-lab/img/lab5/schema-02-game-loop.webp)

_У модели есть возможность сделать один шаг, у экрана — решение, когда его вызвать. Это позволяет отдельно проверять алгоритм и время._

### 5.2. Заменяем ручной обработчик двумя готовыми методами

В **`lib/games/snake/snake_screen.dart`** найдите метод `void _stepOnce()`.

Замените **весь метод `_stepOnce`** следующим блоком из двух методов:

```dart
  void _startMovement() {
    if (_leaving || _game.phase == SnakePhase.running ||
        _game.phase == SnakePhase.edgeStopped) {
      return;
    }
    _cancelTimer();
    if (!_game.start()) return;
    _timer = Timer.periodic(const Duration(milliseconds: 400), _onTick);
    setState(() {});
  }

  void _onTick(Timer timer) {
    if (!mounted || _leaving || timer != _timer ||
        _game.phase != SnakePhase.running) {
      timer.cancel();
      return;
    }
    final moved = _game.step();
    if (!moved) _cancelTimer();
    setState(() {});
  }
```

Таймер живёт в `_timer`. В обработчике проверяется не только существование экрана, но и то, что вызов относится к текущему таймеру. Сам шаг синхронный, без `await`: механизм отложенного AI из ПР4 сюда целиком не переносим.

У края `step` вернёт `false`, а фазу изменит на `edgeStopped`. Поэтому отменяем таймер, но всё равно вызываем `setState`, чтобы показать диагностический статус.

### 5.3. Заменяем промежуточную кнопку

В том же файле найдите **целый `FilledButton` с текстом `Один шаг`**. Замените его:

```dart
                  FilledButton(
                    onPressed: _game.phase == SnakePhase.running ||
                            _game.phase == SnakePhase.edgeStopped
                        ? null : _startMovement,
                    child: Text(_game.phase == SnakePhase.paused
                        ? 'Продолжить' : 'Старт'),
```

Пока движение идёт, кнопка отключена. Метод `_startMovement` также содержит собственную защиту: случайный повторный вызов не создаст ещё один таймер.

В активном коде должен исчезнуть `_stepOnce`. Не оставляйте рядом ещё одну ручную кнопку, которая могла бы добавить внеочередной шаг во время работающего таймера.

## 6. Защищаем направление от быстрого ввода

### 6.1. Текущее направление и запрос — разные данные

Пусть последнее движение было вправо. Между тиками можно нажать «Вверх», но до следующего шага голова ещё не двигалась вверх.

| Момент            | `direction` | `requestedDirection` | Где голова          |
| ----------------- | ----------- | -------------------- | ------------------- |
| После шага вправо | right       | right                | Уже в новой клетке  |
| Нажали вверх      | right       | up                   | Там же, ждёт тик    |
| Наступил тик      | up          | up                   | На одну строку выше |

Если каждый запрос немедленно переписывает `direction`, быстрые `UP → LEFT` превращают RIGHT в LEFT до движения. Защита начинает сравнивать новый запрос с выдуманным промежуточным направлением.

У нас `_requestDirection` не двигает голову и не меняет `direction`. Модель сравнивает запрос с фактическим последним направлением. Это уже закрывает прямой разворот; теперь также сохраним первый принятый поворот до тика.

### 6.2. Одна маленькая самостоятельная проверка

В **`snake_game.dart`**, в `requestDirection`, замените комментарий `// Ограничение второго поворота добавим на этапе 6.` условием:

> Если `requestedDirection` уже отличается от `direction`, новый запрос отклоняется.

Различие означает, что безопасный поворот для следующего тика уже выбран. Возвращаем `false`, не изменяя его.

**Подсказка:** сравнение — `!=`, ранний отказ такой же, как в соседней строке.

Готовый блок:

```dart
    if (requestedDirection != direction) return false;
```

Итоговый метод для сверки:

```dart
  bool requestDirection(Direction next) {
    if (phase != SnakePhase.running || next == direction) return false;
    if (_isOpposite(direction, next)) return false;
    if (requestedDirection != direction) return false;
    requestedDirection = next;
    return true;
  }
```

Это один слот для осмысленного поворота. Нажатие текущего направления или запрещённого противоположного возвращает `false` и слот не занимает. После успешного шага `direction` и `requestedDirection` снова равны — следующий поворот разрешён.

В `pause` незавершённый запрос отменяется присваиванием `requestedDirection = direction`. После возвращения из фона не применится забытое старое нажатие. Позиция тела при паузе сохраняется.

![До тика принимается запрос вверх, второй поворот отклоняется, а фактическое направление меняется только вместе с перемещением головы](/materials/mobile-lab/img/lab5/schema-04-one-turn-per-tick.webp)

_LEFT запрещён ещё и как противоположный RIGHT. Проверка второго DOWN ниже отдельно доказывает работу ограничения одного поворота._

### 6.3. Проверяем четыре направления

Каждый короткий сценарий начинайте через «В начало», затем «Старт». Стрелки принимают запрос только при `running`.

| Действие до ближайшего тика    | Что должно измениться на тике                         |
| ------------------------------ | ----------------------------------------------------- |
| Ничего не нажимать             | col увеличится на 1                                   |
| Нажать вверх                   | row уменьшится на 1, col прежний                      |
| Нажать вниз                    | row увеличится на 1, col прежний                      |
| Вправо, затем вверх            | Повтор текущего направления не мешает запросить вверх |
| Влево сразу из движения вправо | Запрос отклонён, движение вправо продолжается         |

Для допустимого движения влево сначала поверните вверх и **дождитесь настоящего шага вверх**. Затем нажмите влево и дождитесь следующего тика: col уменьшится на 1, row останется прежним.

Ожидаемый путь, если первый поворот успел до первого тика:

```text
(8,8) --UP--> (7,8) --LEFT--> (7,7) --DOWN--> (8,7) --RIGHT--> (8,8)
```

Между стрелками здесь обязательно происходит тик. Это четыре отдельных разрешённых поворота, а не четыре запроса в одном интервале.

### 6.4. Обязательный сценарий UP → LEFT

1. Сбросьте поле и запустите движение вправо.
2. Сразу после видимого шага быстро нажмите вверх, затем влево до следующего тика.
3. На следующем тике голова должна уйти вверх, а не влево.
4. После этого тика новый запрос влево уже допустим.

Если не уверены, что оба нажатия попали между тиками, временно увеличьте `400` до `1500` в единственном `Timer.periodic`. Это только помощь проверке, не настройка игры. После сценариев верните **400** и сохраните файл.

### 6.5. Дополнительная проверка слота UP → DOWN

Из движения вправо до одного тика нажмите вверх, затем вниз. Вниз само по себе не противоположно RIGHT, но второй запрос должен быть отклонён, потому что UP уже принят.

На следующем шаге row уменьшится, а не увеличится. Эта проверка обнаруживает отсутствие ограничения слота, даже если простая проверка противоположных направлений уже работает.

Подождите ещё один тик без нового запроса: движение вверх продолжится. Модель не возвращается автоматически к первоначальному RIGHT после одного поворота.

## Проверяем

1. Прямой LEFT при движении RIGHT отклоняется.
2. `direction` не меняется в обработчике нажатия.
3. UP → LEFT до тика приводит к движению UP.
4. UP → DOWN до тика также сохраняет первый UP.
5. После тика следующий безопасный поворот снова доступен.
6. Временный интервал возвращён к 400 мс.

**Контрольная точка:** запросы не превращаются в несколько фактических поворотов между соседними шагами.

## 7. Проверяем один таймер, край, выход и фон

### 7.1. Повторный запуск не ускоряет движение

В готовом коде три опоры:

1. UI отключает запуск при `running`.
2. `_startMovement` отвергает повторный запуск активной модели.
3. Перед новым разрешённым запуском выполняется `_cancelTimer`.

Стрелки вызывают только `_game.requestDirection`, не создают таймер. `build` рисует текущее состояние; в нём нет `Timer.periodic`.

![Баг ошибочно запускает четыре таймера повторными нажатиями, а Бит показывает один игровой таймер и защищённую кнопку запуска](/materials/mobile-lab/img/lab5/meme-01-two-start-buttons.webp)

_В коде такого ошибочного режима не создаём. В эксперименте ниже будем отключать другое, локальное правило — запрет разворота._

Нажмите «Старт», затем попробуйте нажать его ещё несколько раз: кнопка отключена. Понажимайте стрелки и наблюдайте интервалы изменения подписи — движение не должно учащаться от количества нажатий.

Сделайте три цикла «Старт → В начало». После последнего сброса подождите секунду: три сегмента стоят на месте. Затем запустите снова: темп тот же, а не втрое чаще.

### 7.2. Безопасная остановка у края

Из стартового положения запустите движение вправо и не нажимайте стрелки.

После семи успешных шагов:

```text
[(8,15), (8,14), (8,13)]
```

Следующая предполагаемая голова — `(8, 16)`. Она вне поля, поэтому:

- модель не вставляет её в список;
- тело остаётся `(8,15), (8,14), (8,13)`;
- фаза становится `edgeStopped`;
- обработчик отменяет таймер;
- экран пишет «Край поля — движение остановлено»;
- запуск и стрелки недоступны, работает «В начало».

Подождите ещё две секунды: список не меняется. «В начало» возвращает `ready`, три сегмента и направление вправо; автоматически ничего не запускается.

Это **диагностическая остановка**, а не проигрыш, результат или новая запись в статистике. В ПР7 этот случай получит правила Game Over. Пока не подключайте сохранение и не увеличивайте счётчики ПР4.

Аналогично проверьте верхний край: из начала нажмите «Старт» и сразу вверх. Если успели до первого тика, последняя допустимая голова будет `(0, 8)`. При попытке `(-1, 8)` список останется корректным.

### 7.3. Как готовая обвязка останавливает работу

| Событие                        | Что с таймером                          | Что с моделью/экраном                      |
| ------------------------------ | --------------------------------------- | ------------------------------------------ |
| «В начало»                     | Отмена и `_timer = null`                | Полный reset в `ready`                     |
| Край поля                      | Отмена после отклонённого шага          | `edgeStopped`, допустимое тело сохраняется |
| Приложение потеряло активность | `_pauseMovement` отменяет таймер        | `paused`, запрос направления сброшен       |
| «В GameBox»                    | Отмена до `Navigator.pop`               | Экран помечен `_leaving`                   |
| AppBar Back / системный Back   | `PopScope` отменяет при снятии маршрута | Экран больше не должен двигаться           |
| `dispose`                      | Повторная безопасная отмена             | Освобождается и lifecycle-слушатель        |

`Timer.cancel` можно вызвать повторно. При каждом таком вызове старую ссылку обнуляем; новый запуск создаёт один новый таймер.

`mounted` защищает обращение к экрану, но **не заменяет отмену** работающего таймера. Иначе ненужные обработчики продолжали бы вызываться и после выхода.

### 7.4. Выход во время движения

Проверьте два независимых способа:

1. «В начало» → «Старт» → сразу «В GameBox».
2. На полке подождите секунду, снова откройте змейку: исходное тело, `ready`.
3. Запустите её и вернитесь стрелкой AppBar; на Android повторите системным Back.
4. Снова подождите и откройте игру: скрытого движения не было, новый экран не стартует сам.

Главный экран не создаётся заново для возврата: используется прежний маршрут Home из ПР4. Не заменяйте `Navigator.pop` на `push(HomeScreen(...))`.

После нескольких выходов в терминале не должно быть `setState() called after dispose`. Отсутствие этой ошибки само по себе недостаточно: обязательно проверьте стартовое состояние повторно открытой игры.

### 7.5. Фоновая пауза и явное продолжение

На Android во время движения сверните приложение. Подождите несколько интервалов и вернитесь.

Ожидается:

- тот же допустимый список сегментов, без «догоняющих» шагов;
- статус «Пауза»;
- стрелки отключены;
- кнопка «Продолжить» доступна;
- пока её не нажали, движения нет.

После «Продолжить» идёт один новый таймер. Первый шаг выполняется через интервал, а не несколько раз сразу за прошедшее в фоне время.

В Chrome можно переключиться на другую вкладку или другое приложение. Потеря фокуса может поставить паузу даже без полного сворачивания — это ожидаемое действие `onInactive`. При возвращении также требуется «Продолжить».

`AppLifecycleListener` уже знаком по ПР4. Здесь он снова получает один готовый обработчик `onInactive`; автоматического запуска в `onResume` нет.

## Проверяем

1. Повторный запуск и стрелки не умножают таймеры.
2. На краю нет координат −1 или 16 и нет перехода через стену.
3. Выход обоими способами отменяет движение.
4. Фон сохраняет положение и требует явного продолжения.
5. «В начало» сбрасывает также направление, ожидающий запрос и фазу.

**Контрольная точка:** обязательное движение и его остановка работают. Осталось проверить смысл запрета разворота и приложение целиком.

## 8. Эксперимент «сломайте и исправьте»

Баг предлагает: «Пусть можно будет сразу назад. Что такого?» Проверим на первом шаге, почему запрет нужен ещё до правил столкновения с телом.

### 8.1. Предсказываем невозможное положение

Старт:

```text
direction = right
[(8,8), (8,7), (8,6)]
  голова  шея    хвост
```

Если разрешить LEFT, предполагаемая новая голова — `(8, 7)`. Но эта клетка уже занята шеей, вторым сегментом исходного списка.

После ошибочного шага с обычным добавлением и удалением:

```text
[(8,7), (8,8), (8,7)]
```

Первый и последний элементы теперь совпали. В списке три сегмента, а занятых клеток на поле только две. Это не корректный обычный ход змейки.

Не путайте это с разрешённым проходом через уходящий хвост в будущей полной модели. Здесь длина 3, голова разворачивается в **шею**, которая не освобождается этим шагом.

### 8.2. Временно убираем одно правило

В **`snake_game.dart`**, внутри `requestDirection`, временно удалите **только** эту строку:

```dart
    if (_isOpposite(direction, next)) return false;
```

Ограничение одного поворота, фазу, `step` и удаление хвоста не меняйте. Во время эксперимента анализатор может сообщить о неиспользуемом `_isOpposite`; сам метод не удаляйте, он скоро снова понадобится.

Чтобы успеть прочитать первый шаг, временно замените `400` на `1500` в единственном `Timer.periodic` экрана. Сохраните файлы и выполните hot restart.

### 8.3. Наблюдаем первый ошибочный шаг

1. Откройте змейку, нажмите «В начало».
2. Нажмите «Старт» и сразу влево, **до первого тика**.
3. На первом шаге прочитайте подпись: `(8, 7) → (8, 8) → (8, 7)`.
4. Найдите повтор координаты `(8, 7)`; именно там новая голова совпала со старой шеей.
5. При необходимости переключитесь в редактор: готовая фоновая пауза остановит движение для разбора.

Если успел пройти ещё один тик, положение уже другое. Сбросьте поле и повторите первый шаг; не пытайтесь объяснить более поздний список как начальную ошибку.

Приложение не обязано показать Game Over: столкновение с телом ещё не реализовано. Доказательство здесь — повтор координаты и наложение сегментов. Не добавляйте полную проверку тела ради эксперимента.

### 8.4. Возвращаем защиту

Восстановите удалённую строку перед проверкой занятого слота:

```dart
    if (_isOpposite(direction, next)) return false;
    if (requestedDirection != direction) return false;
```

Верните интервал **400 мс**, сохраните файлы и перезапустите приложение. Нажмите «В начало», чтобы удалить уже испорченное состояние.

Повторите «Старт → сразу влево». LEFT должен быть отклонён; первый шаг вправо даст `(8, 9) → (8, 8) → (8, 7)`.

Затем снова проверьте UP → LEFT и UP → DOWN между тиками. Нельзя исправлять прямой разворот ценой поломки ограничения быстрого ввода.

## Проверяем

1. `_isOpposite` снова вызывается в `requestDirection`.
2. После старта LEFT не создаёт совпадающие сегменты.
3. Буфер первого поворота сохранён.
4. Интервал снова 400 мс; испорченная партия сброшена.
5. Намеренно сломанная версия не закоммичена.

**Контрольная точка:** запрет защищает состояние до появления полноценной проверки столкновений.

## Как восстановиться, если отстали

Сначала сохраните текущую версию в резервной папке или согласованной ветке. Не удаляйте весь GameBox и не переносите заново платформы, имя пакета или Android-конфигурацию.

Восстанавливайте по уровням:

| Уровень        | Действие                                 | Условие перехода дальше                  |
| -------------- | ---------------------------------------- | ---------------------------------------- |
| 1. Координата  | Полный GridPosition по 2.2               | row/col и равенство совпадают с образцом |
| 2. Старт       | Модель по 3.3, экран по 4.1              | Три сегмента стоят без Timer             |
| 3. Ручной step | Смещение по 3.4, хвост по 3.5            | Кнопка даёт ожидаемые три координаты     |
| 4. Список      | Сверка insert/removeLast                 | Голова добавлена, последний хвост удалён |
| 5. Timer       | Два метода по 5.2 и кнопка по 5.3        | Одна кнопка запускает один цикл          |
| 6. Направления | Итоговый requestDirection по 6.2         | Оба быстрых сценария проходят            |
| 7. Lifecycle   | Обвязка экрана по 4.1 и проверки этапа 7 | Выход и фон отменяют движение            |

При восстановлении экрана из 4.1 он опять будет содержать промежуточную кнопку «Один шаг». После ручной проверки обязательно повторите **обе** замены этапа 5. `Timer.periodic` не появится только от наличия поля `_timer`.

### Готовый окончательный step для сверки

Если потерялся порядок операций, замените **только метод `step` целиком**:

```dart
  bool step() {
    if (phase != SnakePhase.running) return false;
    final next = requestedDirection;
    final newHead = _nextHead(next);
    if (!_inside(newHead)) {
      phase = SnakePhase.edgeStopped;
      requestedDirection = direction;
      return false;
    }

    direction = next;
    snake.insert(0, newHead);
    snake.removeLast();
    requestedDirection = direction;
    return true;
  }
```

Сверьте ветку UP с `return head.shifted(-1, 0);`, а итоговый `requestDirection` — с 6.2. Оставшиеся методы берутся из 3.3. Не оставляйте две версии одного метода в классе.

Личное оформление возвращайте после обязательных проверок. Не копируйте из ошибочной версии целые обработчики поверх рабочего checkpoint. Подготовленная преподавателем копия должна соответствовать концу ПР4 или конкретному этапу этой ПР, а не начинать GameBox заново.

## Дополнительное задание: клавиатура в Chrome

Только после обязательной части и двух checkpoint. Экранные стрелки сохраняются. Для ПР6 это улучшение не требуется.

В **`snake_screen.dart`** после импорта Material добавьте:

```dart
import 'package:flutter/services.dart';
```

Внутри `_SnakeScreenState`, **перед методом `_buildCell`**, вставьте готовый обработчик:

```dart
  KeyEventResult _onKeyEvent(FocusNode node, KeyEvent event) {
    final direction = switch (event.logicalKey) {
      LogicalKeyboardKey.arrowUp || LogicalKeyboardKey.keyW => Direction.up,
      LogicalKeyboardKey.arrowDown || LogicalKeyboardKey.keyS => Direction.down,
      LogicalKeyboardKey.arrowLeft || LogicalKeyboardKey.keyA => Direction.left,
      LogicalKeyboardKey.arrowRight || LogicalKeyboardKey.keyD => Direction.right,
      _ => null,
    };
    if (direction == null) return KeyEventResult.ignored;
    if (event is KeyDownEvent) _requestDirection(direction);
    return KeyEventResult.handled;
  }
```

Теперь оберните корневой `PopScope` в `Focus`. В методе `build` замените **строку `return PopScope<void>(`** следующим началом:

```dart
    return Focus(
      autofocus: true,
      onKeyEvent: _onKeyEvent,
      child: PopScope<void>(
```

Остальное содержимое PopScope сохраняется. В конце **этого же build**, непосредственно перед последней строкой `);`, закрывающей возвращаемый виджет, добавьте одну строку `),` для PopScope. Итоговое окончание файла будет таким:

```dart
        ),
      ),
      ),
    );
  }
}
```

Последние три закрытия относятся к `Scaffold`, `PopScope`, `Focus`; строки выше продолжают закрывать прежнюю вёрстку. Выполните форматирование документа в редакторе: отступы вложенного PopScope выровняются. Не вставляйте второе тело `build`.

Этот обработчик использует **тот же `_requestDirection`**, что и экранные кнопки. Отдельного поля змейки, второго таймера и второго набора правил нет. Повтор при удержании клавиши не создаёт движение: запрос отправляется только для `KeyDownEvent`, а известные управляющие клавиши поглощаются обработчиком.

Проверьте в Chrome после «Старт»: стрелки и WASD поворачивают по тем же правилам. При UP → LEFT между тиками действует общий запрет. До запуска и на паузе клавиатура не перемещает тело; не назначайте отдельный step на пробел или каждое нажатие.

Если клавиши не доходят, щёлкните внутри страницы приложения, а не в адресной строке, и проверьте обёртку `Focus`. При нехватке времени вернитесь к обязательному экрану без клавиатуры.

## Перед следующей работой

Змейка умеет повторять шаги с постоянной длиной, поворачивать и останавливаться. Игрок может вести её по полю, пока не остановится у края или сам не прервёт движение.

Возникает следующий вопрос: **«А зачем ей вообще куда-то двигаться?»**

Бит смотрит на пустое поле: **«Движение есть. Теперь нужна цель.»** В ПР6 появится еда и причина менять путь. Сегодня сохраняем рабочий цикл; яблоко в версию ПР5 не добавляем.
